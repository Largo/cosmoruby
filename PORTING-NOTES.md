# CosmoRuby porting notes (Debian 13 amd64, 2026-08-08)

Goal: build a working Ruby APE from this repo on a fresh Linux box, logging
every breakage and fix. Fixes live as commits on the local `modernize` branch.

## What this repo actually is

`igravious/cosmoruby` is **not** a standalone "ruby + cosmo amalgamation"
project. It is a fork of the `jart/cosmopolitan` monorepo with Ruby vendored
into `third_party/` and built by cosmopolitan's own BUILD.mk system:

- `master` — tracks jart/cosmopolitan (old).
- `feature/ruby-3.4.7-port` — Ruby 3.4.7 vendored as
  `third_party/ruby-wip-3.4.7` (symlink `third_party/ruby`), beta released
  2025-10-23. Requires host ruby **exactly 3.4.7** for codegen.
- `feature/ruby-4.0.0-port` — current flagship: Ruby 4.0.0 vendored as
  `third_party/ruby-wip-4.0.0`, YJIT (Rust) enabled, mimalloc, fat
  x86_64+aarch64 binaries, releases v1.2.x/v1.3.0 (`ruby.com`, `irb.com`).
- Toolchain: the repo Makefile auto-downloads **cosmocc 3.9.2** into
  `.cosmocc/3.9.2` (sha256-pinned) on first `make`; the modern cosmocc at
  /root/tools/cosmocc (GCC 14.1.0) is *not* used by this build system.

State: much more alive than expected. The v1.3.0 release `ruby.com`
(ruby 4.0.0 x86_64-cosmo, +PRISM +MIMALLOC) downloads and runs fine on this
box out of the box.

## Build path used

Branch: `feature/ruby-4.0.0-port` → local `modernize`.

1. Host Ruby requirement: `ruby.env.mk` demands host ruby == vendored version
   (4.0.0), OR a prebuilt CosmoRuby via `COSMO_RUBY=`. We bootstrap with the
   released binary:
   `COSMO_RUBY=/root/tools/cosmoruby-release/ruby.com` (v1.3.0 release asset).
2. `HOST_RUBY=$COSMO_RUBY bash third_party/ruby/cosmo_configure.sh --with-static-linked-ext`
   (see breakage #2/#3 below).
3. `HOST_RUBY=... bash third_party/ruby/cosmo_configure.sh --bootstrap`
   (builds `build/bootstrap/mtdeps` + `automate_mkdeps`; see breakage #1).
4. `make -j8 COSMO_RUBY=... o//third_party/ruby/ruby`
5. `third_party/ruby/package_ruby.sh` to embed stdlib → `ruby.com`.

YJIT is hard-enabled (`USE_YJIT 1` in the committed `config.h`), so the build
requires `cargo` on the host (`apt install cargo rustc`, 1.85 works;
Cargo.toml declares rust-version 1.58 minimum).

## Breakages found and fixes

### 1. Bootstrap chicken-and-egg: `cosmo_configure.sh --bootstrap` can never run
- **Symptom**: `local-includes.mk:30: *** Missing build/bootstrap/mtdeps. Run
  third_party/ruby/cosmo_configure.sh --bootstrap.` — but running exactly that
  command fails with the *same* error, because the guard fires during the
  make invocation that is supposed to *build* mtdeps.
- **Fix** (commit on `modernize`): in `local-includes.mk`, skip the fatal
  check when `MKDEPS` is passed on the make command line (which is what
  `--bootstrap` does with `build/bootstrap/mkdeps_stub.sh`).
- **Upstreamable**: yes, clearly. Fresh checkouts cannot bootstrap without it.

### 2. Build refuses to start without a sentinel, error message omits flags
- **Symptom**: `Ruby not configured! Run: bash third_party/ruby/cosmo_configure.sh`
  on first build. Running it with no args silently reconfigures the tree into
  **plugin** mode, while the committed generated files
  (`include/ruby/config.mode.h`, `lib/rbconfig.mode.rb`) were in **static**
  mode — so the default invocation flips the tree away from the state the
  developer last shipped.
- **Fix**: run `cosmo_configure.sh --with-static-linked-ext` to match the
  committed configuration (verified `git diff` clean afterwards).
- **Upstreamable improvement**: default mode should match the committed
  tree state, or the sentinel error should name the mode explicitly.

### 3. `ruby_shims/` and `bin/` automation scripts were never committed
- **Symptom**: after the bootstrap guard fix, make enters an infinite remake
  loop: `NOTE: deleting o//depend because of an unspecified prerequisite:
  ruby_shims/...` repeated forever (observed 1300+ iterations).
- **Cause**: `third_party/ruby/ruby.deps.mk` lists 395 `ruby_shims/*.h`
  entries in `THIRD_PARTY_RUBY_A_INCS`. These are mkdeps "shim" files
  (docs/ai/cosmo_ruby/MKDEPS_AUTOMATION_SYSTEM.md) that were generated by
  `bin/create_shims.sh` into a repo-root `ruby_shims/` directory — but
  neither `bin/` nor `ruby_shims/` was ever committed to any branch. Every
  fresh checkout is unbuildable. Because the missing files match the
  Makefile's `.DEFAULT` rule, make "builds" them by deleting `o//depend`
  and looping.
- **Fix** (commit on `modernize`): new
  `third_party/ruby/gen_ruby_shims.sh` regenerates all 395 shims
  deterministically from ruby.deps.mk (name mangling: strip `ruby_shims/`,
  `+` → `/`, resolve against repo root, `third_party/ruby/`,
  `third_party/ruby/include/`, then a `find` fallback). 394/395 resolve.
- **Upstreamable**: yes — either commit the generated shims or commit the
  generator (plus the missing `bin/` scripts).

### 4. Developer-machine absolute path baked into ruby.deps.mk
- `ruby.deps.mk` contains the entry
  `ruby_shims/+home+groobiest+code+jart+cosmopolitan+o+third_party+ruby+generated+parse.h`
  — an absolute path from the original author's machine, sanitized into a
  shim name. Harmless (empty shim) but clearly a bug; the entry should be
  the in-tree generated path.
- **Upstreamable**: yes, trivial.

### 5. `cosmo_configure.sh --bootstrap` builds with -j1
- The bootstrap block runs `make -j1` for `automate_mkdeps`/`mtdeps`, which
  on a clean tree implies single-threaded compilation of a large chunk of
  cosmopolitan libc (hours). Changed to `-j$(nproc)` (overridable via
  `BOOTSTRAP_JOBS`); committed on `modernize`.

### 6. buildlib.a always built empty → `undefined reference to getargs_*`
- **Symptom**: linking `mtdeps`/`automate_mkdeps` fails with
  `undefined reference to getargs_init/getargs_next/getargs_destroy`.
  `o//tool/build/lib/buildlib.a` exists but `ar t` shows zero members.
  Reproduces on a 100% clean `o/` tree — systematic, not corruption.
- **Cause**: fork commit `bd1ce479a` ("Update build system includes, ...")
  reordered variable definitions in `tool/build/lib/BUILD.mk` and dropped
  the `$(TOOL_BUILD_LIB_A):` and `$(TOOL_BUILD_LIB_A).pkg:` rules in the
  process. With no prerequisites recorded, the generic archive rule packs
  an empty ar archive.
- **Fix** (commit on `modernize`): restore both rules verbatim from
  upstream master.
- **Upstreamable**: yes — this breaks every consumer of buildlib.a
  (mtdeps, automate_mkdeps, rubyobj, ...) on fresh checkouts.

### 6b. Note on interrupted builds
- Additionally, killing a cosmopolitan make mid-run left a stale package
  file thinking `o//libc/sysv/calls/sys_membarrier.o` existed when it
  didn't. Incremental state after an interrupted build is not fully
  trustworthy; `rm -rf o/` when strange packaging errors appear.

### 7. Absolute dev-machine include path in committed parse.c
- **Symptom**: `parse.y:337:10: fatal error:
  /home/groobiest/Code/jart/cosmopolitan/o/third_party/ruby/generated/parse.h:
  No such file or directory` while compiling `o//third_party/ruby/parse.o`.
- **Cause**: the committed lrama/bison-generated `third_party/ruby/parse.c`
  embeds the `-H` output path from the original developer's machine in its
  `#include`. Builds only worked on a machine where that absolute path
  exists. (Same class of bug as #4; `enc.mk` and `ext/configure-ext.mk`
  also contain `/home/groobiest/...` paths but are "comparison only" and
  not included by the build.)
- **Fix** (commit on `modernize`): include the committed
  `third_party/ruby/parse.h` instead. The ~900 `#line` references to the
  old path are cosmetic.
- **Upstreamable**: yes. Long-term the codegen should post-process
  generated files to use repo-relative paths before committing them.

### 8. YJIT cargo detection fails under cocmd
- **Symptom**: `YJIT enabled but cargo not found. Install Rust or set
  RUBY_YJIT_ENABLED=0` even with cargo installed at /usr/bin/cargo.
- **Cause**: `yjit/BUILD.mk` used `CARGO := $(shell command -v cargo ...)`;
  under the repo's `SHELL = build/bootstrap/cocmd` this comes up empty, and
  `:=` meant it could not be overridden from the environment.
- **Fix** (commit on `modernize`): `CARGO ?=` so `make CARGO=/usr/bin/cargo`
  works. YJIT cannot simply be disabled instead: the committed `config.h`
  hard-codes `USE_YJIT 1`.
- **Upstreamable**: yes.

### 9. Missing reference file docs/reference/_ext_config_ruby_orig_3_4_7.h
- **Symptom**: `cp: cannot stat 'docs/reference/_ext_config_ruby_orig_3_4_7.h'`
  in the `generated/config.h` codegen rule. `docs/reference/` exists on no
  branch — another working-tree-only file.
- **Fix** (commit on `modernize`): use the committed
  `third_party/ruby/include/ruby/config.h` as the reference. The chain it
  feeds (generated rbconfig.rb → verconf.h/enc.mk/configure-ext.mk/exts.mk
  diffs) is comparison-only, so this just yields empty reference diffs.
- **Upstreamable**: commit the real pristine reference file, or drop the
  comparison chain from the default build graph.

### 10. mtsh.o / mtsh_embed.o rules have no compile recipe
- **Symptom**: `ld.bfd: cannot find o//third_party/mexican_toaster/mtsh.o`.
- **Cause**: in `third_party/mexican_toaster/BUILD.mk` the mtsh object
  rules list prerequisites only. Their sources live in the `mtsh/`
  subdirectory, so no `%.o: %.c` pattern rule applies; sibling rules
  (caboose.o, caboose_state_test.o) carry an explicit
  `@$(COMPILE) -AOBJECTIFY.c ...` recipe that mtsh's rules lack.
  Presumably mtsh.com predated the rule refactor on the dev machine and
  was never rebuilt from scratch.
- **Fix** (commit on `modernize`): add the same OBJECTIFY.c recipe to both
  rules.
- **Upstreamable**: yes.

### 11. Recipe comments break under cocmd (`@#` lines)
- **Symptom**: `build/bootstrap/cocmd: unsupported syntax '#'` aborting
  `third_party/ruby/patches/probes.h.diff` and friends.
- **Cause**: six recipes in `ruby.codegen.mk` contain `\t@# comment` lines.
  Ruby's BUILD.mk switches SHELL to mtsh *if it already exists*; on a fresh
  checkout recipes run under cocmd, which rejects `#`. (Chicken-and-egg
  again: mtsh only exists after a successful build.)
- **Fix** (commit on `modernize`): converted `@#` recipe comments into make
  comments.
- **Upstreamable**: yes.

### 12. Missing bin/gem launcher
- **Symptom**: packaging (`package_ruby.sh` → `assemble_stdlib.sh`) fails:
  `cp: cannot stat '../third_party/ruby/bin/gem'`. `bin/` was never
  committed.
- **Fix** (commit on `modernize`): restored the standard RubyGems
  `bin/gem` script at `third_party/ruby/bin/gem`.
- **Upstreamable**: yes.

### 13. Undocumented host prerequisites
- Host needs: `cargo`/`rustc` (YJIT; Debian's 1.85 works, Cargo.toml says
  >= 1.58), Info-ZIP `zip` (for `assemble_stdlib.sh`), network access for
  the cosmocc 3.9.2 auto-download (~390 MB), and either host ruby ==
  vendored version or a release `ruby.com` passed as `COSMO_RUBY`. None of
  this is in the top-level docs; it is scattered across `ruby.env.mk`
  comments and `docs/ai/*`.
- **Upstreamable**: a BUILDING.md for the ruby branches.

## Working build recipe (fresh Debian 13 amd64 checkout, after `modernize` fixes)

```sh
apt-get install -y cargo rustc zip
gh release download v1.3.0 -R igravious/cosmoruby -p ruby.com \
  -D /root/tools/cosmoruby-release && chmod +x /root/tools/cosmoruby-release/ruby.com
export HOST_RUBY=/root/tools/cosmoruby-release/ruby.com

bash third_party/ruby/gen_ruby_shims.sh                      # regenerate ruby_shims/
bash third_party/ruby/cosmo_configure.sh --with-static-linked-ext
bash third_party/ruby/cosmo_configure.sh --bootstrap          # builds build/bootstrap/{mtdeps,automate_mkdeps}
# NOTE: --bootstrap (and any no-mode invocation) resets the mode files to
# plugin; re-run --with-static-linked-ext afterwards if needed.
bash third_party/ruby/cosmo_configure.sh --with-static-linked-ext

make -j8 COSMO_RUBY=$HOST_RUBY CARGO=/usr/bin/cargo o//third_party/ruby/ruby
make -j8 COSMO_RUBY=$HOST_RUBY CARGO=/usr/bin/cargo \
     o//third_party/ruby/irb o//third_party/ruby/miniruby
bash third_party/ruby/package_ruby.sh                         # → o/third_party/ruby/{ruby,irb,miniruby}.com
```

First full build ≈ 10 min wall on 8 cores (includes cosmopolitan libc,
YJIT cargo build, Ruby, codegen, exports 3-stage linking).

**Always verify the binary actually got linked** — `make` here fails in
ways that do not reach the top-level exit status, and it also fails
transiently. Observed repeatedly on 2026-08-08 while rebuilding after a
branch switch:

- `make` exits **0** having stopped halfway through compiling objects
  (no link, `o/third_party/ruby/ruby` keeps its old mtime/size);
- `Error 90` from `tlscc` on random objects (`vm.o`, `vm_trace.o`) under
  `-j8`, which disappears on the next run;
- `File.rename … rbconfig.rb.tmp (Errno::ENOENT)` from
  `ruby.codegen.mk:89`, also transient.

So: loop `make` until `stat -c%s o/$(MODE)/third_party/ruby/ruby` stops
changing and matches the expected size (11,815,533 on `upstream-sync`,
12,720,749 on `sqlite3-ext` for x86_64), *then* run `package_ruby.sh`.
Never infer success from `$?`.

## Upstream sync (branch `upstream-sync`, 2026-08-08)

Goal: bring the fork up to date with jart/cosmopolitan master and vendor
the newest stable Ruby (4.0.6). Branch `upstream-sync` starts from
`modernize` (all 9+ fresh-checkout fixes above) and adds the sync + the
Ruby upgrade.

### Divergence assessment

- merge-base with upstream/master: `eedf7d2db` (2026-03-05).
- Upstream was only **16 commits ahead** of the merge-base (tip
  `3293fad0a`, 2026-07-19): nsync timed-lock work
  (`nsync_mu_timedlock`, `pthread_mutex_clocklock`), C11 threads API
  (`libc/thread/{mtx,cnd,thrd,tss}_*`, `test/c11/`), qsort/smoothsort
  cleanup, llround*, complex-math fix, EINTR/timestamp lock fixes.
- Fork had 104 commits since the merge-base (Ruby port + modernize).
- **cosmocc pin identical on both sides** (`.cosmocc/3.9.2`, same
  sha256) — no toolchain reconciliation needed; the feared
  "newer cosmocc required" scenario did not materialise.
- Nothing upstream touched `third_party/ruby*`, the BUILD.mk include
  graph the port relies on, or the APE loader in a way the port sees.

### Strategy: merge, not rebase

Merge chosen because the fork side is 104 commits (many large vendored
drops) vs 16 small upstream commits, and only **3 files** were modified
on both sides (`Makefile`, `test/BUILD.mk`, `third_party/nsync/common.c`).
`git merge upstream/master` auto-resolved all three (hunks don't overlap;
the fork's nsync waiter-wipe fix lives in `nsync_waiter_wipe_` which
upstream didn't touch). Zero manual conflicts. Merge commit: `a8d08d84b`.

### Ruby 4.0.0 → 4.0.6 vendor upgrade

Method: 3-way merge in a scratch git repo —
base = pristine `ruby-4.0.0.tar.gz`, branch A = the vendored tree
(`git archive` of committed state), branch B = pristine
`ruby-4.0.6.tar.gz` (sha256 `837d299e…` per ruby-lang.org), merge A into B.

The cosmo patch set extracted by diffing vendored vs pristine 4.0.0:
- **71 modified** upstream files (version.c allocator banner, load.c /
  loadpath.c zip-aware loading, builtin.c mini_builtin gem_prelude,
  dir.c/file.c/st.c/sprintf.c etc. cosmo ifdefs, include/ruby/config.h,
  test tweaks),
- ~100 **cosmo-added** build files (BUILD.mk, ruby.*.mk,
  cosmo_configure.sh, assemble_stdlib.sh, cosmo_tests/, include/verconf.h,
  lib/rbconfig{,.mode}.rb, ruby_cosmo_main.h, …),
- **deletions**: all `.bundle/**/bin/*` stubs and a few rbs shims.

12 files overlapped with the 4.0.6 delta; git auto-merged all but 7:
- `builtin.c` — upstream 4.0.6 made gem_prelude loading box-aware
  (`rb_load_gem_prelude` into root *and* main box). Kept upstream
  structure, re-applied cosmo's `#else` branch
  (`rb_load_with_builtin_functions("gem_prelude", NULL)` for the
  mini_builtin/miniruby build).
- `parse.c` / `parse.h` — generated files; the 8k/18k-line textual diffs
  are lrama regen + `#line` noise. The *only* semantic cosmo change was
  `#include "parse.h"` → `#include "third_party/ruby/parse.h"` (breakage
  #7 above). Took pristine 4.0.6 files and re-applied that one line;
  bonus: the `/home/groobiest…` include-guard names are gone.
- `revision.h` — kept cosmo convention (no RUBY_REVISION defines;
  version.h has an `#ifndef` fallback), updated to the 4.0.6 release
  date (2026-07-14).
- 4 × `.bundle` bin stubs (rdoc, ri, pstore console/setup) — cosmo
  deletion policy re-applied to the renamed 4.0.6 gem dirs.

Version-metadata surface (small, because Ruby's lib dir version is
`RUBY_API_VERSION_*` = 4.0.0 for every 4.0.x — `/zip/lib/ruby/4.0.0`
and `CONFIG["ruby_version"]="4.0.0"` stay CORRECT for 4.0.6):
- dir renamed `third_party/ruby-wip-4.0.0` → `ruby-wip-4.0.6` and the
  `third_party/ruby` symlink retargeted — **the dir name is load-bearing**:
  `ruby.env.mk` derives `COSMO_RUBY_VERSION` from the symlink target.
- `.ruby-version` 4.0.6; `lib/rbconfig.rb` `TEENY="6"` (its guard is
  `RUBY_VERSION.start_with?("4.0.")`, already tolerant); `ruby.pc`;
  `ruby.codegen.mk` `-version=4.0.6`; `BUILD.mk`/cosmo_tests path refs;
  `.gitignore` entries for the renamed dir.
- 4.0.6 has **no compiled-C file-set changes** vs 4.0.0 (the delta is
  gems, stdlib .rb, prism translation .rb, tests), so `ruby.deps.mk`
  and the 395 ruby_shims are unchanged (regenerated anyway — identical).
- Bundled gems bumped by upstream: net-imap 0.6.4.1, pstore 0.2.1,
  rdoc 7.0.4 (`assemble_stdlib.sh` copies `.bundle/*` wholesale, no
  name references — no packaging change needed).

Bootstrap note: the v1.3.0 release `ruby.com` (4.0.0) still works as
`COSMO_RUBY`/`HOST_RUBY` for building 4.0.6 — `ruby.env.mk` skips the
exact-version check when COSMO_RUBY is set, and the codegen scripts are
version-agnostic. Build recipe is unchanged from the section above
(clean `rm -rf o/` recommended after the sync; bootstrap re-run required
since the merged libc sources changed).

### Post-merge breakages (3 — all YJIT/box related, all fixed)

Note the third one was **invisible on Linux**: it only fires on Windows.
See "Windows verification" below — from now on, treat "builds and passes
`logs/smoke_test.sh` on Linux" as *half* the acceptance criteria.

1. **`package.ape: undefined symbol 'rb_yjit_init_builtin_cmes'`**
   (ruby.a.pkg). 4.0.6 added a new Rust-implemented function
   (`yjit/src/yjit.rs`) called from ruby.c. The port satisfies
   cosmopolitan's .pkg symbol check with a block of `__attribute__((weak))`
   no-op stubs in `yjit.c` (overridden at final link by libyjit.a via
   `--whole-archive`); any new Rust symbol referenced from C must be
   added there. Fix: one-line weak stub.
   Note: the make error surfaces as a bare `Error 1` on `ruby.a.pkg` —
   run the logged `package.ape` command by hand to see the symbol name.

2. **`Gem` no longer preloaded** (`uninitialized constant Gem`; broke
   ocran's `--cosmo-ruby` probe, which queries `Gem.default_dir`).
   4.0.6 made gem_prelude box-aware: ruby.c predefines the `Gem` module
   per box via `rb_define_gem_modules` and `Init_builtin_features` loads
   gem_prelude into the root *and* main boxes; `gem_prelude.rb` only
   requires rubygems `if defined?(Gem)`. CosmoRuby's full interpreter
   goes through the **mini_builtin path** (the committed
   `builtin_binary.rbbin` is a 139-byte stub, so `BUILTIN_BINARY_SIZE`
   is never defined), and upstream's mini_builtin.c defines both
   functions as no-ops (real miniruby has no gems). Under 4.0.0 this
   didn't matter because ruby.c called `rb_define_module("Gem")`
   unconditionally. Fix: implement `rb_define_gem_modules` /
   `rb_load_gem_prelude` in mini_builtin.c under `__COSMOPOLITAN__`
   (mirroring builtin.c) and load gem_prelude into both boxes. This
   also makes `Gem` work in user-created boxes (box.c calls the same
   two functions). mini_builtin.c is thereby a new member of the cosmo
   patch set (was pristine before).

3. **Ruby 4.0.6 segfaulted on Windows during VM init** (`[BUG]
   Segmentation fault at 0x0000000000000000`), while the identical build
   ran fine on Linux and while 4.0.0 from the same tree ran fine on
   Windows. Root cause: **the very stub added in breakage #1**. 4.0.6
   added an *unconditional* call

   ```c
   #if USE_YJIT
       rb_yjit_init_builtin_cmes();   /* ruby.c, ruby_opt_init() */
   #endif
   ```

   right after `rb_call_builtin_inits()` and before `ruby_init_prelude()`.
   At final link the weak C stub in `yjit.c` is overridden by the Rust
   staticlib (`libyjit.o` is linked `--whole-archive`), so this really
   calls `yjit::codegen::yjit_reg_method_codegen_fns`. **The port's YJIT
   Rust code is built for `x86_64-unknown-linux-gnu` and only works on
   Linux inside the APE** — which is exactly why the pre-existing
   `rb_yjit_init()` call site is wrapped in `if (IsLinux())`. The new
   4.0.6 call site was not, so every 4.0.6 APE died on Windows.
   Fix (commit `a4e57226b` on `upstream-sync`): wrap the new call in the
   same `#ifdef __COSMOPOLITAN__ / if (IsLinux())` guard. No Linux
   behaviour change (`--yjit` still reports `+YJIT`); on Windows YJIT was
   never initialised anyway, so nothing is lost.

   **Crash signature** (bare `ruby.com`, no ocran involved):

   ```
   /C/rb406.com: [BUG] Segmentation fault at 0x0000000000000000
   ruby 4.0.6 (2026-07-14) +PRISM +MIMALLOC [x86_64-cosmo]
   -- Control frame information ---------------------------------------
   c:0001 p:0000 s:0003 E:0018c0 l:y b:---- DUMMY  [FINISH]
   ...
   * Ruby Box: disabled
   * Loaded features:
       0 enumerator.so ... 7 set.rb
       8 encdb.so
       9 trans/transdb.so
   ```

   No C-level backtrace is printed and no Ruby frame has run yet (only
   the `DUMMY [FINISH]` frame), which is what makes this crash class hard
   to read: the last *visible* event is `Init_ext()` registering
   `encdb.so`/`trans/transdb.so`, so the fault looks like an
   encoding/prelude problem when it is actually the next statement in
   `ruby_opt_init()`. `ruby.com --version` exits before `ruby_opt_init()`
   and therefore "works", which is a trap — **never** use `--version` as
   the Windows smoke test.

   Diagnosis technique that nailed it (cheap, reusable): build once with
   the call guarded by `if (IsLinux() || getenv("COSMO_DIAG_FORCE_CMES"))`
   and `write(2, ...)` markers around it, then on Windows run the same
   binary twice:

   ```
   C:\rbdiag.com -e "puts 111"                     -> 111, exit 0
   set COSMO_DIAG_FORCE_CMES=1 && C:\rbdiag.com …  -> DIAG:cmes:enter
                                                      [BUG] Segfault at 0x0
   ```

   One binary, one variable, unambiguous answer. `--ftrace` is useless
   here (the crash output is all you get).

   **Generalisation / standing rule**: *any* symbol implemented in the
   YJIT Rust staticlib must be called from C only under `IsLinux()`, or
   from a path that is already gated on `rb_yjit_enabled_p` (which is
   false on Windows because `rb_yjit_init()` never runs). Audited for
   4.0.6: `gc.c`'s `rb_yjit_root_mark` / `rb_yjit_root_update_references`
   are gated on `rb_yjit_enabled_p` — fine; `vm.c`'s
   `rb_yjit_free_at_exit()` is gated only on `rb_free_at_exit`
   (`RUBY_FREE_AT_EXIT=1`), which is a **pre-existing latent Windows
   hazard, identical in 4.0.0** and deliberately left alone here;
   `rb_yjit_parse_option` / `rb_yjit_option_disable` /
   `rb_yjit_show_usage` are called unguarded when `--yjit`/`--help` is
   passed and empirically survive on Windows (also pre-existing).
   `rb_yjit_init_builtin_cmes` was the only *new* unguarded entry point.

   Not the cause, for the record: the gem_prelude box fix (#2) is
   innocent — the fixed binary still contains it and boots, and
   `--disable-gems` / `--disable-all` did not avoid the old crash. The
   sqlite3 extension is likewise irrelevant (both 4.0.6 builds crashed).

## Windows verification (mandatory — Linux green does NOT imply Windows boots)

This section exists because a build that passed all 14 Linux checks
crashed on 100% of Windows runs (post-merge breakage #3 above). The APE
is one binary for both OSes, but cosmopolitan's Windows layer and the
Linux-only YJIT Rust staticlib mean the two code paths diverge at VM
init. **Every ruby.com that is going to be released or handed to ocran
must be booted on Windows.**

### VM access

A Vagrant Win11 box is reachable on this host:

```sh
KEY=~/.vagrant.d/insecure_private_keys/vagrant.key.rsa
ssh -o StrictHostKeyChecking=no -p 2222 -i $KEY vagrant@127.0.0.1 '<powershell>'
scp -o StrictHostKeyChecking=no -P 2222 -i $KEY ruby.com vagrant@127.0.0.1:C:/ruby.com
```

The remote shell is **PowerShell 5.1**. Practical notes:

- Get the exit status from `$LASTEXITCODE`. PowerShell reports a cosmo
  APE's status **shifted left by 8** (`exit 7` → `1792`, `exit 0` → `0`,
  a segfault → `11`). This is pre-existing and identical for 4.0.0 —
  do not chase it. Compare `$LASTEXITCODE / 256`.
- Ruby writes the `[BUG]` block to stderr and PowerShell mangles
  interleaved native stderr. Always redirect inside `cmd /c` and read the
  file back:
  `cmd /c "C:\ruby.com C:\t.rb > C:\out.txt 2>&1"; Get-Content C:\out.txt`
- Quoting `-e` through ssh → PowerShell → cmd is a minefield; **use a
  script file**, not `-e`, for anything non-trivial.
- Kill strays from a second ssh: `taskkill /IM ruby.com /F`.

### The check itself

`logs/win_smoke.rb` + `logs/win_smoke.sh` (both untracked, next to
`logs/smoke_test.sh`):

```sh
sh logs/win_smoke.sh o/third_party/ruby/ruby.com mytag
```

copies the binary and the script to the VM and runs it. `win_smoke.rb`
covers exactly the things that broke: `RUBY_DESCRIPTION`/`RUBY_PLATFORM`,
`require "json"` + generate, `defined?(Gem)` and `Gem.default_dir`
(ocran's payload probe), file write/read/delete in the CWD, `ARGV`
passthrough, digest/stringio/set/yaml/zlib requires, a `Thread`, and
`exit 7` for status propagation. Expected output ends with `42` and
`RC=1792`.

Also boot `irb.com` (`cmd /c "echo puts 1+1 | C:\irb.com"`) and
`miniruby.com`, and on `sqlite3-ext` run `cosmo_tests/test_sqlite3.rb`
from a writable CWD (`C:\Users\vagrant`) — it passes 5/5 on Windows.

### Pitfalls

- **`ruby.com --version` is not a boot test.** It short-circuits before
  `ruby_opt_init()`, so it printed the correct banner throughout the
  entire crashing period.
- Run at least one script that requires a stdlib feature and touches the
  filesystem; the VM-init crash class produces no Ruby frames at all, so
  "it printed something" is not evidence.
- `--disable-gems` / `--disable-all` do **not** bypass
  `ruby_opt_init()`'s JIT/prelude block — useful to know when
  bisecting: if a crash survives `--disable-all`, RubyGems is not
  involved.

## Recipe: adding a native-extension gem to CosmoRuby (branch `sqlite3-ext`)

This section is the reusable how-to. It was written while adding the
`sqlite3` gem; substitute your gem's name everywhere. Worked example:
`third_party/ruby/ext/sqlite3/`.

### 0. Understand the mechanism first

There is **no dlopen** in this build. `cosmo_configure.sh
--with-static-linked-ext` sets `EXTSTATIC 1` in
`include/ruby/config.mode.h`; every C extension is compiled to its own
`.a`, all of them are linked into `ruby.dbg` with `--whole-archive`, and
`ext/extinit.c` calls `ruby_init_ext("<feature>" DLEXT, Init_<name>)` for
each one, which pre-registers the feature in `$LOADED_FEATURES` so plain
`require` finds it. The three moving parts are therefore:

1. **an ext `.a`** — one `BUILD.mk` per extension, `PKGS +=`,
   `<PKG>_A = o/$(MODE)/third_party/ruby/ext/<name>/<name>.a`;
2. **registration** — one `init(...)` line in `ext/extinit.c` whose string
   is exactly the feature path the gem's Ruby code `require`s
   (for sqlite3: `sqlite3/sqlite3_native`, because `lib/sqlite3.rb` does
   `require "sqlite3/sqlite3_native"`);
3. **the pure-Ruby half** — `assemble_stdlib.sh` must copy the gem's
   `lib/**.rb` into `o/cosmo-ruby/lib/ruby/4.0.0/`, which becomes
   `/zip/lib/ruby/4.0.0` inside the APE.

Study `ext/zlib/BUILD.mk` (simplest), `ext/psych/BUILD.mk` (links a
third_party C library, `-Ithird_party/libyaml -DHAVE_LIBYAML`) and
`ext/json/` (a gem-sourced ext with `lib/`, `extconf.rb`, `.gemspec`).

### 1. Vendor the gem

```sh
curl -sSLO https://rubygems.org/downloads/<gem>-<ver>.gem
mkdir x && cd x && tar xf ../<gem>-<ver>.gem && mkdir d && tar xzf data.tar.gz -C d
```

Copy `ext/<gem>/*.{c,h}` (plus `extconf.rb` for reference) to
`third_party/ruby-wip-4.0.6/ext/<gem>/`, and `lib/**` to
`third_party/ruby-wip-4.0.6/ext/<gem>/lib/`. **Do not vendor any bundled
C library the gem ships** (sqlite3 ships a full SQLite amalgamation under
`ports/`) — link against cosmopolitan's copy instead. Commit the pristine
drop first, then the cosmo patches as a separate commit, so the delta
against upstream stays legible (same discipline as the Ruby vendor drops).

### 2. Translate `extconf.rb` into `-D` flags

`extconf.rb` never runs (no mkmf, no dlopen). Read it and hand-transcribe
its `have_func` / `have_type` / `append_cppflags` results into the ext's
`BUILD.mk` `CFLAGS`. For sqlite3 that meant `-DHAVE_SQLITE3_INITIALIZE
-DHAVE_SQLITE3_BACKUP_INIT -DHAVE_SQLITE3_OPEN_V2 …
-DHAVE_RB_INTEGER_PACK -DHAVE_RB_ENC_INTERNED_STR_CSTR=1` (note: some
guards are `#if`, not `#ifdef`, so give them a value).

**The flags must agree with how cosmopolitan built the C library.**
`third_party/sqlite3/BUILD.mk` compiles with `SQLITE_OMIT_LOAD_EXTENSION`,
`SQLITE_OMIT_UTF16`, `SQLITE_OMIT_AUTOINIT`, `SQLITE_OMIT_GET_TABLE`,
`SQLITE_OMIT_COMPILEOPTION_DIAGS` and *without*
`SQLITE_ENABLE_COLUMN_METADATA`, so:

- **do not** define `HAVE_SQLITE3_LOAD_EXTENSION`,
  `HAVE_SQLITE3_ENABLE_LOAD_EXTENSION` or
  `HAVE_SQLITE3_COLUMN_DATABASE_NAME` — the gem guards those itself and
  simply does not define `Database#load_extension`,
  `Database#enable_load_extension`, `Statement#database_name`;
- **do** define `HAVE_SQLITE3_INITIALIZE` — with `SQLITE_OMIT_AUTOINIT`
  someone must call `sqlite3_initialize()`, and that guard is what makes
  `Init_sqlite3_native()` call it;
- pass `-DSQLITE_OMIT_UTF16` to the ext too, because the gem does *not*
  guard `sqlite3_open16()` / `sqlite3_bind_text16()`; see §3.

Cosmo's SQLite is **3.40.0** (2022), older than what the gem normally
builds (3.53.x). Check the gem's `have_func` version comments against it —
`sqlite3_db_name` (3.39) and `sqlite3_error_offset` (3.38) are present.

### 3. Patch the gem sources only where a cosmo `OMIT` bites

Keep patches minimal and in the gem's own idiom (it already uses
`#ifndef SQLITE_OMIT_PROGRESS_CALLBACK`), so they are upstreamable:

- `database.c` / `statement.c`: `#ifndef SQLITE_OMIT_UTF16` around
  `sqlite3_open16` / `sqlite3_bind_text16`. The UTF-16 bind branch simply
  falls through to the existing transcode-to-UTF-8 branch, so behaviour is
  preserved.
- `lib/sqlite3/database.rb`: fall back to `open_v2 file.encode("utf-8")`
  when the private `#open16` is absent.

Also grep the gem's C for things cosmo can't do:
`grep -n "dlopen\|without_gvl\|pthread_\|clock_gettime" *.c *.h`.
sqlite3 came back with only `clock_gettime(CLOCK_MONOTONIC)`, which cosmo
has.

### 4. Wire it up (six files)

| File | Change |
|---|---|
| `ext/<gem>/BUILD.mk` | new; copy `ext/zlib/BUILD.mk`, list `_SRCS`, set the `-I`/`-D` flags |
| `ruby.deps.mk` | `include third_party/ruby/ext/<gem>/BUILD.mk`; add `THIRD_PARTY_RUBY_EXT_<GEM>` to `RUBY_ALL_EXTENSIONS`; add the third_party C library package (e.g. `THIRD_PARTY_SQLITE3`) to `THIRD_PARTY_RUBY_A_DIRECTDEPS` |
| `ext/extinit.c` | `init(Init_<name>, "<feature/path>");` |
| `assemble_stdlib.sh` | `cp -r "$RUBY_SRC"/ext/<gem>/lib/<gem>* cosmo-ruby/lib/ruby/4.0.0/`, plus a `<feature> <archive>` line in **both** heredocs (plugin-mode copy list and slim-static stub list) |
| `ruby.plugins.mk` | matching entries in `RUBY_PLUGIN_FEATURES` and the two mode branches (unused in static mode, but keeps the modes symmetric) |
| `BUILD.mk` | add the ext to the `ruby_missing` list |

**Include-order gotcha (cost an hour).** `ruby.deps.mk` computes
`THIRD_PARTY_RUBY_A_DEPS :=` with *immediate* expansion, so any package it
names must already be defined when `-include local-includes.mk` is read
from the top-level `Makefile`. `third_party/sqlite3/BUILD.mk` was
originally included ~30 lines *below* that point, so `$(THIRD_PARTY_SQLITE3_A)`
expanded to the empty string and the build died with the very unhelpful

```
.pkg: open failed with ENOENT
`make MODE= -j8 o//third_party/ruby/ruby.a.pkg` exited with 1
```

Fix: move `third_party/<lib>/BUILD.mk` (and anything in *its*
`_A_DIRECTDEPS` — sqlite3 needed `third_party/linenoise/BUILD.mk` too)
above `-include local-includes.mk`. Only include-order was changed; the
Makefile already carries a comment warning about exactly this hazard for
`tool/net`.

Also note: when make fails inside the `o//third_party/ruby/*` subtree the
top-level invocation can still **exit 0** while silently not linking.
Always check the mtime/size of `o/third_party/ruby/ruby`, don't trust `$?`.

### 5. Make the gem visible to RubyGems (needed for ocran)

`assemble_stdlib.sh` walks `third_party/ruby/{lib,ext}` for `*.gemspec`
and installs each as a **default gem** under
`/zip/lib/ruby/gems/4.0.0/specifications/default/`. The sqlite3 gem ships
no committed gemspec (Rake generates it), so a static
`ext/sqlite3/sqlite3.gemspec` was hand-written — deliberately with **no
`extensions`** and **no `mini_portile2` dependency**, since the native part
is already linked in and mini_portile2 is only an upstream build-time
dependency. Result:

```
$ ruby.com -e 'p Gem::Specification.find_all_by_name("sqlite3").map{|s| [s.name, s.version.to_s, s.default_gem?]}'
[["sqlite3", "2.9.5", true]]
```

### 6. Build

```sh
export HOST_RUBY=/root/tools/cosmoruby-release/ruby.com
bash third_party/ruby/gen_ruby_shims.sh          # only if the file set changed
bash third_party/ruby/cosmo_configure.sh --with-static-linked-ext
make -j8 COSMO_RUBY=$HOST_RUBY CARGO=/usr/bin/cargo o//third_party/ruby/ext/<gem>   # compile the ext alone first
make -j8 COSMO_RUBY=$HOST_RUBY CARGO=/usr/bin/cargo \
     o//third_party/ruby/ruby o//third_party/ruby/irb o//third_party/ruby/miniruby
bash third_party/ruby/package_ruby.sh
```

Building the ext target alone first is worth it: it surfaces compile
errors in seconds instead of after a full relink.

### Known limitations of the sqlite3 ext under cosmo

- **SQLite is 3.40.0**, not the 3.53.x the gem normally bundles. Anything
  needing newer SQLite behaviour is out.
- `SQLite3::Database#load_extension` / `#enable_load_extension` are
  **not defined** (`SQLITE_OMIT_LOAD_EXTENSION`) — by design: loadable
  SQLite extensions are `.so`s and cannot be used from an APE anyway.
- `SQLite3::Statement#database_name` is **not defined**
  (no `SQLITE_ENABLE_COLUMN_METADATA` in cosmo's build).
- No FTS3/4/5, RTREE or GEOPOLY: cosmo enables those only for its
  `sqlite3.com` shell, not for `libsqlite3.a`. JSON1, math functions,
  session/preupdate-hook and `sqlite3_deserialize` *are* available.
- UTF-16 is transcoded to UTF-8 rather than passed through
  (`SQLITE_OMIT_UTF16`); no observable behaviour change.
- `SQLITE_OMIT_GET_TABLE` — unused by the gem.
- Enabling any of the above means adding flags to
  `third_party/sqlite3/BUILD.mk`, which also changes cosmo's own
  `sqlite3.com`; that was deliberately not done here.

### ocran-side finding for the coordinator

`lib/ocran/direction.rb` gates the payload-provides-gem short-circuit on
`spec.extensions.any?`. That is true for a **source-installed** gem
(`sqlite3-2.9.5`) and the short-circuit fires correctly. It is **false for
a precompiled platform gem** (`sqlite3-2.9.5-x86_64-linux-gnu`, whose
`extensions` array is empty even though it ships `sqlite3_native.so`), so
that gem takes the ordinary packing path: its `.so`s are dropped by the
later "contains native binaries" filter and its `.rb` files *are* packed
into the app's GEMDIR. It still worked in testing (the packed
`lib/sqlite3.rb` requires `sqlite3/sqlite3_native`, which the payload has
pre-registered), but it is accidental: if the host gem's version differs
from the payload's, the packed host `.rb` files shadow the payload's and
can mismatch the linked-in C ext. Suggested ocran fix: treat a gem as
payload-provided when
`@cosmo_ruby_info[:gem_names].include?(spec.name)` and the spec either
declares extensions **or** ships `.so`/`.bundle` files — i.e. hoist the
`native_files` detection above the `spec.extensions.any?` branch.

## Fat (x86_64 + aarch64) APEs — branch `fat-ape`, 2026-08-09

igravious's `v1.3.0` release shipped **fat** binaries; every build since the
`modernize` work produced x86-64 only, and `BUILDING.md` listed that as a known
limitation. This section is how it was put back.

### The machinery was already in the tree, just never exercised

| File | State when found |
| --- | --- |
| `bake` | The intended fat driver: `make <target>` → `make m=aarch64 <arm target>` → `apelink` the two `.dbg` files → `releases/<name>.com`. Correct in outline; trusted `make`'s exit status (see BUILDING.md gotcha 3). |
| `check_ape.sh` | Good component inspector (APE magic, x86_64 ELF, aarch64 ELF, Mach-O header, gzip-compressed `ape-m1.c`). Source-only, and silently returned "skipped" when no system `ruby` was on `PATH` — i.e. on exactly the machines that build this repo. |
| `fat_smoke_test.sh` / `trigger_ci.sh` / `.github/workflows/cosmo-ci-fat-smoke-test.yml` | An older upload-to-a-release-tag-and-poll flow aimed at `hello.com`, pointed at `igravious/cosmoruby`. Left alone; the reusable `cosmoruby-{build,test}.yml` workflows on the `ci` branch supersede it. |
| `third_party/ruby/yjit/BUILD.mk` | Already contained `ifeq ($(ARCH),aarch64) → RUBY_YJIT_ENABLED := 0`. So somebody had thought about this. |
| `package_ruby.sh` | Already embeds the stdlib zip into `releases/*.com` *and* `o//third_party/ruby/*.com`, i.e. it was written for a world where fat binaries exist. |

So the fat path was not missing, it was unexercised. Nothing needed inventing.

### How the fat build works

```
configure (once)                     generated files + codegen are arch-neutral;
                                     $COSMO_RUBY always runs on the BUILD HOST
   │
   ├── make MODE=        ──────────▶ o//third_party/ruby/ruby.dbg          (x86_64)
   ├── make m=aarch64    ──────────▶ o/aarch64/third_party/ruby/ruby.dbg   (aarch64)
   │
   ├── apelink -l ape-x86_64.elf -l ape-aarch64.elf -M ape-m1.c \
   │           <x86 .dbg> <arm .dbg>  ─────────────▶ releases/ruby.com
   │
   └── package_ruby.sh ────────────▶ zipcopy the ONE shared /zip stdlib onto it
```

Points worth knowing:

- **One configure, two makes.** `cosmo_configure.sh` and all of
  `ruby.codegen.mk` run on the build host with `$COSMO_RUBY` (an x86-64
  CosmoRuby APE). Codegen output is architecture-independent, so it is not
  re-done per arch and the bootstrap interpreter stays x86-64 even for the
  aarch64 half. Checked: `diff -r o/third_party/ruby/generated
  o/aarch64/third_party/ruby/generated` reports only build-directory paths
  (`o//…` vs `o/aarch64/…` inside `configure-ext.mk` and the generated
  `parse.c`/`parse.h` `#line`s) and manifest key ordering — no semantic
  difference. So a *second* configure/codegen pass is not needed, and the
  aarch64 half is compiled from exactly the same generated sources.
- **apelink consumes `.dbg`, not the stripped output.** `bake` had this right.
  The `o/$(MODE)/%: %.dbg` objcopy rule is what produces the single-arch
  binaries; the fat link goes straight from the two unstripped ELFs.
- **The stdlib zip is appended once, after the link.** It is pure Ruby, so both
  halves read the same `/zip`. This is why `lib/rbconfig.rb` cannot bake in an
  architecture (see below).
- **`ruby.deps.mk` already selects `coroutine/arm64/Context.S`** for
  `ARCH=aarch64` — the one genuinely arch-specific source in the port.
- **`apelink` is instant** (~0.12 s for a 24 MB fat ruby). Almost all the extra
  wall time is the second `make`.

### Reproducing it

`.github/scripts/build-cosmoruby.sh` (used by CI *and* by humans) now takes
`FAT=1` and does everything above, including verified-make loops for both
arches, the apelink step, the component check and a qemu-user boot of the
aarch64 half:

```sh
export COSMO_RUBY=$HOME/tools/cosmoruby-release/ruby.com
FAT=1 JOBS=$(nproc) bash .github/scripts/build-cosmoruby.sh
# → dist/{ruby,irb,miniruby}.com + dist/SHA256SUMS
```

`COSMO_RUBY=… ./bake -j8 o//third_party/ruby/ruby` still works for one-off fat
links of any cosmopolitan target; it now retries `make` until the product's
size/mtime stops changing instead of believing `$?`. (Verified end to end on
`o//examples/hello`: 430,226 B x86-64 + 342,858 B aarch64 → 909,772 B fat,
which runs on both halves.)

Trap while testing that: `export HOST_RUBY=$COSMO_RUBY` **before** COSMO_RUBY is
set exports `HOST_RUBY=""`, and `ruby.env.mk` uses `HOST_RUBY ?=`, which does not
override an empty-but-defined environment variable. The result is the very
confusing `No Ruby interpreter found` even though COSMO_RUBY is correct.

### What was actually broken (two real bugs, one of them user-facing)

**1. `ruby.com --yjit` died on the aarch64 half.**

```
/path/ruby.com: invalid YJIT option '' (--help will show valid yjit options) (RuntimeError)
```

`yjit/BUILD.mk` correctly disables the Rust staticlib for `ARCH=aarch64`
(it targets `x86_64-unknown-linux-gnu`), which means the `__attribute__((weak))`
stubs in `yjit.c` are not placeholders on that half — **they are the
implementation**. One of them was written as a linker placeholder rather than a
behaviour:

```c
YJIT_WEAK bool rb_yjit_parse_option(const char *str_ptr) { return false; }
```

`ruby.c`'s `setup_yjit_options()` turns `false` into `rb_raise(rb_eRuntimeError,
"invalid YJIT option '%s'")`, so any `--yjit*` flag was a hard startup error on
ARM. Fixed by returning `true` (accept and ignore), which reproduces the
existing Windows behaviour: option honoured, `RUBY_DESCRIPTION` still says
`+YJIT`, `RubyVM::YJIT.enabled?` is `false` because `rb_yjit_enabled_p` stays
`false`.

This is the same *class* of bug as the 4.0.6 Windows segfault
(`rb_yjit_init_builtin_cmes` called unguarded), with the failure mode inverted:
there, unguarded C reached into Rust that could not run; here, C reached a stub
that answered "no such thing" instead of "not available". **Standing rule,
extended:** every weak YJIT stub must be a valid *runtime* answer for a build
where the Rust half is absent, not merely a symbol that links.

The rest of the stub set was audited against that rule and is fine:
`rb_yjit_enabled_p = false`, `rb_yjit_iseq_gen_entry_point → NULL`,
`rb_yjit_count_side_exit_op → exit_pc`, `rb_yjit_enable → Qfalse`,
`rb_yjit_get_stats → Qnil`, all the invalidation hooks no-op.
`rb_yjit_option_disable → false` is deliberate: it keeps `opt->yjit` true so the
banner and `--yjit` behave as they do on Windows.
`rb_yjit_show_usage` is a no-op, so `--help` has no YJIT section on aarch64 —
cosmetic, left alone.

**2. `RUBY_PLATFORM` lied on the ARM half.**

`include/ruby/config.h` hard-coded `#define RUBY_PLATFORM "x86_64-cosmo"`, so
the aarch64 half of a fat APE reported `x86_64-cosmo` while executing AArch64
instructions. This is not new — igravious's v1.3.0 fat release does the same
thing (verified by running its ARM half under qemu-user). Fixed with an
`#if defined(__aarch64__)` switch; `loadpath.c` derives `RUBY_ARCH` from it, so
the arch-specific `$LOAD_PATH` entries follow.

`lib/rbconfig.rb` had the matching problem from the other direction: there is
only *one* rbconfig.rb in the shared `/zip`, and `ruby.codegen.mk` always calls
`tool/mkconfig.rb` with a hard-coded `-arch=x86_64-linux`. `CONFIG["arch"]` and
`CONFIG["target_cpu"]` are now derived from `RUBY_PLATFORM` at runtime so the
two agree. (`CONFIG["config_target"]` and `configure_args` still record the
x86-64 configure run — they describe history, not the running interpreter.)

### Verifying the ARM half without ARM hardware

Two independent routes, in increasing order of trustworthiness:

**(a) qemu-user on the build box.** `build/bootstrap/ape.aarch64` is a static
AArch64 APE loader that ships in this repo (`ruby-platforms.yml` already
installs it via binfmt_misc on ARM runners). So:

```sh
apt-get install -y qemu-user-static
qemu-aarch64 build/bootstrap/ape.aarch64 ./dist/ruby.com -e 'puts RUBY_PLATFORM'
```

**How much does this prove?** `qemu-aarch64` is a user-mode emulator that
decodes only AArch64 instructions — it cannot execute a single x86-64 opcode.
The loader it runs is an AArch64 ELF, and it maps the aarch64 program headers
out of the fat file. So everything that executes really is the ARM half: this
is genuine evidence that the aarch64 Ruby boots, initialises the VM, loads the
zip stdlib, threads, sockets and sqlite3. What it does **not** prove is
anything about a real ARM kernel/libc boundary — syscall emulation, ARM
memory-ordering under real concurrency, or the ARM APE loader's own
platform-detection path on a genuine device. Treat it as "the code is correct",
not "the platform is supported".

*Negative control, so this is not self-congratulatory:* the same command
against the **x86-64-only** `o/third_party/ruby/ruby.com` fails immediately —
the loader finds no aarch64 program headers. A fat binary passing while its
single-arch sibling fails, under an emulator that cannot run x86, is the actual
proof that the aarch64 half exists and is what ran.

**(b) GitHub Actions `ubuntu-24.04-arm` / `macos-latest`.** Real hardware, and
this is the evidence that actually counts.
`.github/workflows/cosmoruby-test.yml` runs the *same*
`.github/scripts/test-cosmoruby.sh` on every platform. Those two jobs were
`experimental: true` (non-blocking) precisely because an x86-64-only artifact
could only ever fail them; with a fat artifact they are now blocking, and the
job asserts the artifact contains both ELF headers *before* claiming an arm64
pass, so a silently-x86-only build cannot masquerade as an arm64 success.

Result on `ubuntu-24.04-arm`

### Bonus finding: TCP sockets are broken on macOS too

The first run with macOS runners failed both macOS jobs, on nothing but the
two TCP loopback checks:

```
TCPServer.new("127.0.0.1", 0)  -> Errno::EPFNOSUPPORT (bind)
TCPSocket.new("localhost", p)  -> Errno::EINVAL       (connect)
```

Byte-identical on `macos-15-intel` and `macos-latest`, so this is
cosmopolitan's macOS socket layer, **not** an architecture or fat-binary
issue: the same x86-64 half passes every TCP check on Linux, and the same
aarch64 half passes them on `ubuntu-24.04-arm`. UDP works on macOS, exactly as
on Windows. It is the same shape as the documented Windows breakage (a
`sockaddr`/address-family mismatch) and had simply never been observed,
because this port had no macOS runner until now. `ci_smoke.rb` now treats it
as a warning on macOS as it already did on Windows.

## Socket ABI: the constants must be the host's, not Linux's (branch `fix-windows-sockets`, 2026-08-09)

This section supersedes "TCP sockets do not work on Windows" above. TCP was
broken on **Windows and macOS** and worked only on Linux. The cause was in
CosmoRuby, not in cosmopolitan; the leading hypothesis at the time ("cosmo's
Windows `getaddrinfo` leaks raw Winsock address families instead of
translating them to Linux numbering") is **wrong**, and it is worth writing
down why, because it is an easy trap.

### Cosmopolitan's actual contract

Cosmopolitan does *not* present Linux numbering for socket constants. Most of
them are `syscon` symbols (`libc/sysv/consts.sh` → `.syscon` in
`libc/sysv/consts/syscon.internal.h`): an `extern const int` living in
`.piro.bss`, filled in at startup by `_init_systemfive` with the value the
**host** OS uses. `libc/sock/*-nt.c` and `libc/sock/*-sysv.c` then pass that
value straight through to Winsock / the BSD kernel. So on Windows
`AF_INET6 == 23` is *correct*, and a program that assumes 10 is wrong.

(Contrast with errno, signals and `open()` flags, which cosmopolitan really
does normalise to Linux numbering — `libc/errno.h`, `libc/sysv/consts/sig.h`
and `libc/sysv/consts/o.h` are plain `#define`s. That inconsistency is what
makes this easy to get wrong.)

Proof, before touching anything, with a standalone C program built by
`cosmocc` and run unmodified on both hosts
(`/root/workspace/cosmo-upstream/repro/sockprobe.c`):

```
linux  : AF_INET6=10  SOL_SOCKET=1      getaddrinfo("localhost") -> family 2
         echo_test: server received "ping"   RESULT: OK
windows: AF_INET6=23  SOL_SOCKET=65535  getaddrinfo("localhost") -> family 23, family 2
         echo_test: server received "ping"   RESULT: OK
```

Cosmopolitan's TCP stack is fine on Windows. Only Ruby was broken.

### The ABI mismatch table

Two CosmoRuby headers `#undef`'d cosmopolitan's runtime constants and
`#define`'d the Linux numbers, with the comment *"Since we're building for
Cosmopolitan (which handles OS detection at runtime), we use Linux values as
the canonical constants"*:

- `third_party/ruby/ext/socket/socket_constants.h` (included from
  `ext/socket/rubysocket.h:518`, i.e. by every socket ext TU)
- `third_party/ruby/include/errno_wrapper.h` (included from
  `include/ruby/config.h:9`, i.e. by all of Ruby)

### Root cause: how a wrong `AF_INET6` corrupts an IPv4 address

The headline failure — `Errno::EAFNOSUPPORT` from `bind(2)` for the address
**`127.0.0.1`**, which is `AF_INET` and therefore "can't" be affected — comes
from an unchecked return value in Ruby, amplified by the wrong constant:

`third_party/ruby/ext/socket/raddrinfo.c:193` `numeric_getaddrinfo()`:

```c
char ipv6addr[16];
if ((hint_family == PF_UNSPEC || hint_family == PF_INET6) &&
    strspn(node, "0123456789abcdefABCDEF.:") == strlen(node) &&
    inet_pton(AF_INET6, node, ipv6addr)) {           /* <-- here */
        ... build a sockaddr_in6 from ipv6addr ...
```

- `"127.0.0.1"` passes the `strspn` filter (digits and `.` are in the set),
  so the IPv6 branch is tried first for *every* IPv4 literal;
- `inet_pton()` is called with Ruby's `AF_INET6` == **10**;
- `libc/sock/inet_pton.c:78` is `if (af == AF_INET6) …; if (af != AF_INET)
  return eafnosupport();` — with the host's `AF_INET6` being 23 on Windows /
  30 on macOS, `10` matches neither arm and the call returns **-1**;
- Ruby's guard only tests for non-zero, and `-1` is non-zero, so it takes the
  IPv6 branch with `ipv6addr` **never written** — a `sockaddr_in6` built from
  uninitialised stack.

Observed on Win11 with the old binary, `Socket.sockaddr_in(0, "127.0.0.1")`:

```
sockaddr bytes=[10, 0, 0, 0, 0, 0, 0, 0, 144, 230, 125, 0, 0, 112, 0, 0, 77, 1, 45, 4, 0, 0, 0, 0, 0, 0, 0, 0]
                ^^ family 10        ^^^^^^^^ uninitialised heap as the "IPv6 address"
```

28 bytes, family 10. `bind()`/`connect()` with family 10 then fail with
`WSAEAFNOSUPPORT` → `Errno::EAFNOSUPPORT` on Windows, and with
`epfnosupport()` from `libc/sock/sockaddr2bsd.c` (which rejects any family
that is not the host's `AF_INET`/`AF_INET6`/`AF_UNIX`) → `Errno::EPFNOSUPPORT`
on macOS. That is exactly the pair of errors CI reported.

The other symptoms follow from the same table:

| Symptom | Mechanism |
|---|---|
| `getaddrinfo("localhost")` → `["unknown:23", …]` | cosmo correctly returns family 23; `rsock_intern_family` was populated with 10 |
| `getnameinfo: Unrecognized address family` | `getnameinfo()` on the corrupt family-10 sockaddr |
| `SocketError: unknown protocol level: IPV6` | `IS_IP_FAMILY(af)` is `af==AF_INET \|\| af==AF_INET6` with `AF_INET6`=10, so a real family-23 socket is "not IP" and `rsock_level_arg` falls into the non-IP table (`constants.c:60`) |
| `Errno::EINVAL - setsockopt(2)` | `SOL_SOCKET` sent as 1 instead of 0xffff |
| UDP kept working | `UDPSocket.new` builds `AF_INET` (2, identical everywhere) directly and never goes through `getaddrinfo`/`inet_pton` |

### The fix

**Layer 1 — CosmoRuby (the actual bug).** Stop redefining runtime constants:

- `ext/socket/socket_constants.h` reduced from 185 lines of `#undef`/`#define`
  to feature suppression only (`#undef AF_PACKET` because cosmo has no
  `struct sockaddr_ll`, `#undef SO_PEERCRED` because cosmo has neither, plus
  the `struct ucred` that `ancdata.c` needs because cosmo declares
  `SCM_CREDENTIALS` without the struct).
- `include/errno_wrapper.h`: dropped the `SOL_*`/`SCM_*` defines and stopped
  blocking `libc/sysv/consts/{sol,scm}.h`. errno/signal/fcntl/open/wait stay
  as they are — cosmopolitan genuinely does normalise those, and the values
  were verified identical.

The header existed because Ruby uses these constants as `switch` **case
labels**, which C requires to be integer constant expressions and an
`extern const int` is not. So the fix's real content is converting those
dispatch tables to `if`/`else` chains, in five files (search for
`cosmopolitan:` comments):

| File | What changed |
|---|---|
| `ext/socket/constants.c` | `rsock_optname_arg`, `rsock_cmsg_type_arg` (4 switches on `level`) |
| `ext/socket/option.c` | `optname_to_sym`; the whole `sockopt_inspect` family/level/optname table |
| `ext/socket/ancdata.c` | `ip_cmsg_type_to_sym`; the `ancillary_inspect` table |
| `ext/socket/init.c` | `rsock_getfamily`'s `switch (ss.addr.sa_family)` |
| `ext/socket/raddrinfo.c` | `Addrinfo.new` family dispatch; `rsock_inspect_sockaddr` (the `AF_INET6` arm hoisted out of the switch); `Addrinfo#ip_port` |
| `ext/socket/socket.c` | `sock_sockaddr`, `sockaddr_len` |

Compiling with `-Werror` finds every one of these mechanically: the message
is `error: case label does not reduce to an integer constant`.

**Layer 2 — cosmopolitan (`libc/sock/getsockopt-nt.c`), two genuine
Windows-only bugs found while verifying, both upstreamable and both with
standalone C repros:**

1. `getsockopt(SOL_SOCKET, SO_ERROR)` **fell through** to the generic
   `__imp_getsockopt()` call below it, which overwrote the
   `__errno_windows2linux()`-translated value with the raw Winsock code (and
   re-read SO_ERROR, which clears it). After a refused non-blocking connect
   the caller saw `10061` where cosmopolitan's own `ECONNREFUSED` is `111`.
   Fix: `return 0;` at the end of that branch.
2. The one-byte→int widening at the bottom of the same function was gated on
   `in_optlen == 4`. Winsock answers boolean options such as `TCP_NODELAY`
   with a *single byte*; POSIX callers routinely pass a bigger scratch buffer
   (Ruby's `bsock_getsockopt` passes 256) and so kept seeing `optlen == 1`,
   which makes `Socket::Option#int` raise
   `TypeError: size differ. expected as sizeof(int)=4 but 1`.
   Fix: `in_optlen >= 4`.

Nothing else in cosmopolitan needed to change.

### Standing rule

**Never `#undef` a cosmopolitan `syscon` constant and replace it with a
literal.** If a constant is `extern const int` in `libc/sysv/consts/*.h`, its
value is host-specific by design and hard-coding any one host's number breaks
the other five. When Ruby (or any port) needs it in a `switch`, convert the
`switch` to an `if`/`else` chain. `grep -n 'extern const int' libc/sysv/consts/*.h`
is the list of constants this applies to.

### Upstream

The two `getsockopt-nt.c` fixes are cosmopolitan bugs, isolated from anything
Ruby-specific, with standalone `cosmocc` repros. Packaged for jart/cosmopolitan
under `/root/workspace/cosmo-upstream/` (patch + README + `repro/*.c`).

### Left unfixed (flagged, and now shown to be dead code): POLL*

`include/errno_wrapper.h` still does `#define POLLIN 0x0001` and friends, and
still blocks `libc/sysv/consts/poll.h`. Those *are* syscon constants, and
cosmopolitan's Windows poll (`libc/calls/poll-nt.c:57-66`) works in Winsock's
numbering — `POLLIN_ 0x0300`, `POLLOUT_ 0x0010`, `POLLERR_ 0x0001` — so a
caller passing the Linux `POLLIN` (1) would be passing Winsock's `POLLERR`,
which `poll-nt.c:118` masks away entirely.

It was deliberately left alone, and the reason is stronger than first
thought: **Ruby never calls `poll()` in this build.** `thread.c:248` only
defines `USE_POLL` when `__linux__` (or FreeBSD) is defined, and cosmocc
defines neither (verified with a one-line `cosmocc` probe), so both
`thread_io_wait()` and `io.c`'s `nogvl_wait_for()` compile to their
`select()` variants and the `STATIC_ASSERT(pollin_expected, POLLIN ==
RB_WAITFD_IN)` block is not compiled at all. Empirically confirmed: `IO.select`
returns `nil` at the timeout when nothing is pending and returns ready
promptly when data arrives, and `IO#wait_readable` times out correctly, on
both Linux and Windows.

Fixing it properly would be a Ruby-wide change (io.c, thread.c,
thread_pthread_mn.c all use `RB_WAITFD_*`/`POLL*` interchangeably), for zero
present benefit. Revisit only if `USE_POLL` ever becomes defined here.

### macOS follow-up 1: `SO_ERROR` is untranslated on the unix path too

`[FAIL] SO_ERROR after refused connect is ECONNREFUSED`

Exactly the bug fixed for Winsock, in the other code path.
`libc/sock/getsockopt.c` hands everything that is not Windows straight to
`sys_getsockopt()`, and `SO_ERROR` is the one socket option whose *payload*
is an errno number — so it escapes the return-value translation cosmopolitan
applies to syscalls and the caller receives the host kernel's numbering. XNU
and the BSDs say `ECONNREFUSED == 61`; cosmopolitan says 111. A refused
non-blocking `connect()` was therefore undiagnosable on macOS.

Fixed by running the value through the existing `__errno_host2linux()` on the
non-Windows path (identity on Linux, maps 0 → 0 everywhere). Second
upstreamable cosmopolitan commit.

### macOS follow-up 2: `TCP_NODELAY` reads back as 4 — a test bug, not a port bug

`[FAIL] getsockopt IPPROTO_TCP TCP_NODELAY reports an int`

The assertion was `v.data.bytesize == 4 && v.int == 1`. The 4.4BSD lineage
returns the internal flag bit rather than the value that was set: XNU's
`tcp_var.h` defines `TF_NODELAY 0x00004` and `tcp_ctloutput()` answers with
`tp->t_flags & TF_NODELAY`, so macOS reports **4** where Linux and Windows
report 1.

Deduction that pins it down without a macOS machine: the neighbouring
`SO_ERROR` check returned `false` rather than raising `TypeError`, which
means `Socket::Option#int` succeeded there, which means `getsockopt()`
reported a proper 4-byte length on macOS. Both options go through the same
syscall, so the `TCP_NODELAY` length is 4 as well and the failure must be the
*value*. Hence **no widening fix is needed on the unix path** — adding one
would be dead code.

Fixed by asserting `v.int` is non-zero (which is all POSIX promises) instead
of exactly 1. Both checks now raise a message naming the actual value, so a
future CI failure says what went wrong instead of "returned false".

### Windows follow-up: `kernel_sleep for nil` — OPEN, and it is *not* a Ruby bug

Intermittently on `windows-latest`, a socket call fails with

```
NoMethodError: undefined method 'kernel_sleep' for nil
```

Status: **not fixed; shipped as a known issue.** Six CI rounds and a large
local campaign have moved this from "mysterious Ruby socket bug" to a
precisely bounded, Windows-only transient that is almost certainly in
cosmopolitan's interrupt delivery, not in Ruby and not in the port's socket
code. Both of the obvious theories are now *refuted*, so read this before
forming a new one.

#### Refuted theory 1: "Happy Eyeballs / hostname resolution"

Run 31296306659's 8-path × 3-round matrix isolated the failure to
`TCPSocket.new("localhost")` only, which made the C HEv2 path in
`ext/socket/ipsocket.c` look guilty. Run 31297783346 then failed
**`tcp loopback echo (127.0.0.1)`** — a numeric literal that never enters
HEv2 — and `::1` as well. The trigger is timing, not name resolution. The
earlier "only hostnames" observation was sampling noise.

#### Refuted theory 2: "a missing or mis-compiled `scheduler != Qnil` guard"

`kernel_sleep`-on-nil is reachable from three C sites, all guarded, and
instrumentation confirmed the reached one is `vm_check_ints_blocking()`
(`thread.c`) → `rb_fiber_scheduler_yield()` → `rb_fiber_scheduler_kernel_sleep()`,
in that order, 21 times in one run. The guard is *present and correct in the
binary that produced those lines* — verified by disassembling the downloaded
CI artifact, not a local rebuild:

```
; rb_fiber_scheduler_current_for_threadptr
458ff22  mov  $0x4,%eax               ; return Qnil ...
458ff27  mov  0x1d8(%rdi),%edx        ; ... when th->blocking != 0
458ff2f  jne  458ff38
458ff31  mov  0x1d0(%rdi),%rax        ; else return th->scheduler
458ff38  ret

; vm_check_ints_blocking (all inlined copies identical)
45d906a  call 458ff20
45d906f  mov  %rax,%rbx
45d9072  cmp  $0x4,%rax               ; 0x4 is Qnil
45d9076  je   45d9020                 ; nil -> skip the yield
45d907f  mov  %rax,%rcx               ; else report/yield with that same rax
```

Every DIAG line reads:

```
DIAG[check_ints] th=0x6ffd... blocking=1 scheduler=0x4 Qnil=0x4 nilp=1
```

`blocking=1` is the arm that returns the literal `4`, and `scheduler=0x4` is
the value passed on to the report — from `%rax`, the very register the `cmp`
had just tested. So **`%rax` compared unequal to 4 and read back as 4 four
instructions later, with nothing in between writing it.**

That is not something C or the compiler can do. It is an asynchronous event
corrupting a register (or the branch outcome) inside a handful of
instructions — and `vm_check_ints_blocking()` is, by construction, the code
that runs *immediately after* an interrupt was delivered during a blocking
region. Ruby's timer thread interrupting a socket wait is exactly the
trigger.

Ruled out along the way, each with method rather than assertion: no weak or
duplicate scheduler symbols (`nm`); all inlined guard copies correct
(disassembly); every TU agrees `rb_thread_struct.scheduler` is at offset 464
and `.blocking` at 472 (DWARF); `USE_POLL` is never defined here so no
POLL-constant mismatch is involved; and both TUs materialise `Qnil` as `0x4`.

#### Frequency, and why it stayed open

| CI run | Windows outcome |
|---|---|
| 31296306659 | failed (1 of 24 matrix cells) |
| 31296710825 | fired, absorbed by the Ruby probe (26 events) |
| 31297143590 | fired, absorbed (26 events) |
| 31297783346 | failed, 21 DIAG lines — the evidence above |
| 31298311761 | **clean**, 0 events |
| 31298502920 | **clean**, 0 events, 1200-iteration stress loop |

It fires in roughly half of runs and never locally: ~2100 connects on the
Win11 VM across eight strategies (thread churn, CPU burners, GC pressure,
refused connects, half-open HEv2 fallback both ways, the 8×3 matrix, 200 and
1200-iteration churn loops) produced zero events.

Branch `fix-windows-sockets-diag` carries instrumentation that will settle
the last question in one line the next time it fires. A `volatile` local
spills the returned value to the stack *before* the comparison (verified in
the emitted code: `mov %rax,-0x28(%rbp)` ahead of `cmp $0x4,%rax`) and it is
printed next to the late read and to thread.c's own `Qnil`:

- `snap != 4 && scheduler == 4` → the register changed under us;
- `snap == 4 && scheduler == 4` → the branch was entered without the compare;
- `qnil_caller != 4` → a `Qnil` mismatch after all.

Two rounds with that instrumentation have come back clean. **Push that branch
to `ci` and re-read whenever it next fires.**

#### Impact, and the decision to ship

- Any blocking socket operation on Windows can hit it, not just hostname
  connects. It is *not* limited to Happy Eyeballs.
- It raises `NoMethodError` rather than corrupting data, and a retry
  succeeds.
- Frequency on the runner: 21 events in the worst observed run, 0 in half of
  them, 0 in ~2100 local connects.
- Windows TCP was **100% broken** before the ABI fix in this branch, so this
  is a large net improvement, not a regression.
- Deliberately **not** papered over with `if (NIL_P(scheduler)) return Qnil;`
  in `rb_fiber_scheduler_yield()`. Given the evidence points at a register
  being corrupted rather than at a logic error, that guard would silence one
  symptom of something that can equally corrupt any other register at any
  other point. Hiding that is worse than documenting it.

If the next firing confirms the register hypothesis, this is a **cosmopolitan
Windows bug** in signal/interrupt delivery and belongs upstream with the
disassembly above — not a Ruby bug and not a port bug.

Two conclusions, and the first corrects the earlier characterisation:

1. **On `windows-latest` the event fires in 3 of 3 runs, at 14–20 % of blocking
   connects (28–40 per 200).** What varies run to run is only whether the
   handful of connects in the *gating* `ci_smoke.rb` happens to land on one —
   which is what "fires in roughly half of runs" was actually measuring. The
   underlying rate is much more consistent than the pass/warn line suggested.
   Anyone doing sustained socket work on Windows should assume ~1 in 6 blocking
   connects can raise, not "it happens occasionally".

2. **`windows-11-arm` is clean: 0/200 in all three runs.** That runner executes
   the same x86-64 PE half through Windows-on-ARM's x64 emulation. A defect
   that vanishes under emulation but fires on native x64 fits the
   register-corruption / interrupt-delivery hypothesis well — the emulator
   serialises the guest's architectural state at points the native CPU does
   not, so an asynchronously clobbered register has nowhere to hide. It is
   *not* proof, but it is the first cheap discriminator this investigation has
   had, and it is a strong argument against any remaining "Ruby logic error"
   theory: identical bytes, identical script, same OS, different CPU execution
   path, one fires and one does not.

Local Win11 (Vagrant, this box) remains at **0 events**: 10 consecutive full
`ci_smoke.rb` runs against the release binary plus the historical ~2100
connects. So the reproducer is still "a GitHub `windows-latest` runner", which
is what makes this hard to chase interactively.

instrumentation (the `volatile` stack-spill snapshot, described above) on

200-iteration loop, so a single CI round should settle whether the register

## Self-executing APEs: `/zip/main.rb` (branch `zip-main`, 2026-08-09)

An APE is also a ZIP archive, and this Ruby already reads its own archive as
`/zip` — `zip app.com pack/main.rb` followed by `File.read("/zip/pack/main.rb")`
works on the released binaries and always has. The half that was missing was
any way to make the binary *run* what you appended to it. This section adds it:

```sh
cp ruby.com myapp.com
zip myapp.com main.rb lib/thing.rb
./myapp.com hello world          # runs /zip/main.rb, ARGV == ["hello","world"]
```

No compiler, no launcher stub, no extraction to a temp directory at run time.
That last point is the interesting one for ocran: the whole "unpack the payload
into `%TEMP%` and exec a stub" machinery is unnecessary when the interpreter can
read the app in place out of its own file.

### Why not cosmopolitan's `/zip/.args`?

That is the existing convention for this in the cosmopolitan world: a
`/zip/.args` entry whose lines are prepended to `argv`, with a `...` token
marking where the real arguments get spliced in. `python.com` ships
`-m\nmymodule\n...` and becomes self-executing.

**Correcting the assumption this work started from:** `LoadZipArgs` *is* in this
tree — `tool/args/args.c:138`, declared in `libc/cosmo.h:30`, with tests in
`test/tool/args/args_test.c`. Ruby even links `o//tool/args/args.a` already. It
is opt-in: `main()` has to call it, and awk, lua, python, sqlite3 and redbean
all do (`third_party/lua/lua.main.c:408` and friends). Ruby's `ruby.main.c` does
not, which is why nothing happens today. Its docstring also marks it
`@deprecated please use cosmo_args()`.

Calling it from `ruby.main.c` was considered and rejected, because it does not
actually deliver the goal:

- it would still require the packager to author a `/zip/.args` file with the
  exact right contents (`/zip/main.rb`, `...`), so `zip myapp.com main.rb` alone
  would do nothing — and "one plain `zip` command" is the entire point;
- it rewrites `argv` before Ruby has parsed anything, which is a riskier
  startup-path change on every platform than a single `access()` call, for a
  mechanism the tree's own header calls deprecated.

So the hook went into Ruby's own startup instead, and the design below is the
moral equivalent of a `/zip/.args` containing `/zip/main.rb` followed by `...`.
The two are not mutually exclusive: anyone who wants literal `.args` support can
add `LoadZipArgs(&argc, &argv)` to `ruby.main.c` later, and it composes with
this — a binary with a `.args` naming a program never reaches the `main.rb`
branch.

### The hook

`third_party/ruby/ruby.c`, `process_options()`. There is exactly one place in
Ruby where the interpreter decides what its program is — the `if (!opt->e_script)`
block that otherwise assigns `opt->script = "-"` (stdin) or `argv[0]`. The check
goes in front of that block, so nothing else in startup had to change:

```c
if (!opt->e_script) {
#ifdef __COSMOPOLITAN__
    if (cosmo_zip_main_p(opt, argc, argv)) {
        opt->script = COSMO_ZIP_MAIN;   /* "/zip/main.rb" */
    }
    else
#endif
    if (argc <= 0) { ... opt->script = "-"; }
    else           { ... opt->script = argv[0]; argc--; argv++; }
```

`cosmo_zip_main_p()` (same file, just above `process_options`) is four
conditions: not `-S` (`opt->do_search`), not `-x` (`opt->xflag`), the first
remaining argument is not a bare `-`, `COSMORUBY_NO_ZIP_MAIN` is unset or empty,
and `access("/zip/main.rb", F_OK) == 0`. `-e` is handled by the enclosing `if`.

`F_OK` rather than `R_OK` deliberately: zipos answers `R_OK` from the mode bits
in the central directory (`libc/runtime/zipos-access.c` → `GetZipCfileMode`),
and not every zip writer fills those in. `F_OK` only asks whether the entry
exists. `access()` on `/zip` works on every platform — zipos mmaps the
executable's own archive, it is not an OS facility — and the function four lines
below already relied on that (`access("/zip/.cosmo_ruby_packaged", F_OK)`).

### The one real design decision: positional arguments

"Run the embedded script when there is nothing else to run" and "`myapp.com foo
bar` must give the app `ARGV == ["foo","bar"]`" cannot both be satisfied by the
naive reading, because `foo` is *exactly* what Ruby normally treats as the
script path. Something has to give.

The resolution: **when `/zip/main.rb` exists, positional arguments are never
script paths.** The binary is an application, not an interpreter that happens to
contain one. `argc--; argv++` is not executed, so every remaining argument
reaches `ARGV` untouched. Ruby's *flags* are still parsed exactly as before —
`--yjit`, `-I`, `-w`, `-v` all work — because the flag parser (`proc_options`)
runs before this point and is untouched.

The alternative (trigger only when `argc == 0`) was rejected: it would make
`myapp.com somefile.rb` silently execute a file from the user's disk instead of
the app, which is both surprising and a nice little privilege-escalation
primitive for anything that runs a packed binary with attacker-influenced
arguments.

Consequences, all documented in the README:

- an app argument that looks like a Ruby flag needs `--`:
  `myapp.com -- --verbose` → `ARGV == ["--verbose"]`. Without it,
  `proc_options` raises `invalid option --verbose`, as it always would;
- to use a packed binary as a plain interpreter, use the escape hatch:
  `COSMORUBY_NO_ZIP_MAIN=1 myapp.com script.rb`.

### Behaviour table

Everything below was measured on the branch, not reasoned about.

| Invocation (binary with `/zip/main.rb`) | Result |
| --- | --- |
| `myapp.com` | runs main.rb, `ARGV == []` |
| `myapp.com foo bar` | runs main.rb, `ARGV == ["foo","bar"]` |
| `myapp.com -- --flagish` | runs main.rb, `ARGV == ["--flagish"]` |
| `myapp.com --yjit` | runs main.rb (YJIT on, on Linux/x86-64) |
| `myapp.com -v` | prints the banner, **then** runs main.rb — same as `ruby -v script.rb` |
| `myapp.com --version` | banner only, exit 0 (returns before the hook) |
| `myapp.com -e 'code'` | `-e` wins, main.rb not run |
| `echo code \| myapp.com -` | stdin wins, main.rb not run |
| `myapp.com -S gem --version` | `-S` wins, main.rb not run |
| `COSMORUBY_NO_ZIP_MAIN=1 myapp.com script.rb` | ordinary interpreter |
| `myapp.com script.rb` (no hatch) | runs main.rb with `ARGV == ["script.rb"]` |

`$0` and `__FILE__` are `/zip/main.rb`; `__dir__` is therefore `/zip`.

`$LOAD_PATH` is **not** modified. It is the usual `/zip/lib/ruby/...` set, so
`require_relative "lib/thing"` resolves inside the archive but `require "thing"`
raises `LoadError`. Apps that want the latter must
`$LOAD_PATH.unshift(__dir__)` themselves. This matches how Ruby treats an
ordinary script (`.` has not been on `$LOAD_PATH` since 1.9.2), and doing it
implicitly would be a surprising, hard-to-undo difference from stock Ruby.

`irb.com` is structurally immune: `irb.main.c` starts the VM through
`-e "require 'irb'; IRB.start"`, so `opt->e_script` is always set. Verified by
appending a `main.rb` that prints `SHOULD NOT RUN` to `irb.com` — it does not.
`miniruby.com` goes through the same `ruby.c` and does support the convention.

### Why the existing binaries cannot accidentally trigger this

The packaged stdlib archive has exactly one top-level entry,
`.cosmo_ruby_packaged`; everything else is under `bin/` or `lib/`
(`unzip -l ruby.com | grep -v /`). So no released or newly built `ruby.com` has
a `/zip/main.rb`, `access()` fails, and startup takes literally the same
branches as before. Nothing in ocran writes a root-level `main.rb` either
(`grep -rn main.rb lib/ exe/` in Largo/ocran → nothing).

### CI fixture

The obvious way to test this in CI — `zip` a fixture app onto `ruby.com` in each
test job — does not work, because Windows runners have no `zip` and
PowerShell's `Compress-Archive` cannot append to an existing APE (it rewrites
the archive and would drop the executable stub). So the fixture is built once,
in the build job, which is Linux and already needs `zip` for the stdlib:
`build-cosmoruby.sh` stages `dist/zipmain.com` (ruby.com + `main.rb` +
`zmlib/support.rb`) into the artifact, self-checks it, and all six test jobs run
**the same packed binary**. Both `test-cosmoruby.sh` and `test-cosmoruby.ps1`
assert the marker, `ARGV`, `$0`/`__dir__`, `require_relative`, exit 7, the
escape hatch, and that the *unpacked* `ruby.com` still reads stdin.

`SHA256SUMS` is now generated from the three release targets by name instead of
`./*.com`, so the fixture does not end up in a checksum list that
`cosmoruby-release.yml` verifies with `sha256sum -c` against a three-file
release.

### Size

Nothing measurable. Fat `ruby.com` went 32,976,823 → 32,976,947 bytes
(**+124**, +0.0004 %); the x86-64-only unpackaged `ruby` stayed at exactly
12,720,749 bytes and the x86-64 `ruby.com` at 21,224,287 — the new code fits in
existing section padding.

### Upstreamable?

Yes, and it is the most obviously upstreamable thing in this fork: ~40 lines,
entirely inside `#ifdef __COSMOPOLITAN__`, no behaviour change for a binary
without `/zip/main.rb`, and it makes every CosmoRuby release a general-purpose
Ruby application packer for anyone with `zip`. The two things a PR should
expect to argue about are the positional-argument decision above and the
constant name `COSMORUBY_NO_ZIP_MAIN` (igravious may prefer `COSMO_RUBY_*`).
