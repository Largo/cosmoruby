## Overview

Cosmopolitan Libc is a C library that enables "build-once run-anywhere" binaries. It creates Actually Portable Executables (APE) that run natively on Linux, macOS, Windows, FreeBSD, OpenBSD, NetBSD, and BIOS without interpreters or virtual machines.
CosmoRuby is our port of Ruby to Cosmopolitan. We're working on CosmoRuby primarily.

## Communication Style for Code Changes

**CRITICAL: When proposing fixes or changes, use humble, uncertain language:**

- Use "should" not "will" or "has"
- Say "this might fix X because Y" not "this fixes X"
- Always end with "let's test to verify if this works"
- NEVER claim success until the user confirms it works
- Acknowledge uncertainty - debugging is an iterative process
- Be humble about predictions

**Examples:**
- ❌ BAD: "Perfect! I've fixed the issue."
- ✅ GOOD: "This change should help because X. Let's test to see if it actually works."

**Why:** Code changes are hypotheses that must be verified through testing. Claiming success before verification is overconfident and unhelpful.

## Build System

### Building

The build system uses GNU Make with custom tooling. The Makefile will automatically download cosmocc (the Cosmopolitan C compiler) if not present.

**IMPORTANT: Always use `-j1` when providing `make` commands to the user.** The user controls parallelism themselves.

**Primary build commands:**
```bash
make -j1           # Build everything (default mode)
make -j1 MODE=dbg  # Debug mode with sanitizers
make -j1 MODE=opt  # Optimized build
make -j1 MODE=rel  # Release mode
make -j1 MODE=tiny # Minimal size binaries
```

**Build individual targets:**
```bash
make -j1 o//examples/hello                  # Build single binary
make -j1 o//test/posix/signal_test          # Build single test
make -j1 o//test/posix                      # Build all tests in package
```

**Build modes (set with MODE= or m=):**
- Default/empty: Optimized with backtraces, strace, ftrace
- `dbg`: Debug mode, -O0, ubsan, stack canaries
- `opt`: Highly optimized (-O3), backtraces enabled
- `rel`: Release mode, no asserts, numeric backtraces
- `tiny`: Minimal binaries (can be as small as 12kb)
- `optlinux`: Fastest mode, Linux-only
- `tinylinux`: Minimal size, Linux-only
- `sysv`: Unix systems only (no Windows)
- `aarch64`: ARM64 architecture

**Architecture:**
- x86_64 is the default on x86_64 hosts
- aarch64 is the default on ARM hosts
- Build for aarch64 explicitly: `make m=aarch64`

**Output directory structure:**
```
o/$(MODE)/          # All build artifacts go here
o/$(MODE)/*.dbg     # Debug symbols
o/$(MODE)/*         # Final stripped binaries
```

### Testing

**Run tests:**

```bash
make -j1 -O check              # Run all test checks
make -j1 o//test/posix         # Build and run tests in package
o//test/posix/signal_test      # Run individual test directly
```

**Test with special flags:**


**Always run tests before committing** (per user's global instructions).

### Clean Build

```bash

rm -rf o//libc o//test        # Clean specific packages
make clean_toolchain          # Remove toolchain artifacts
```

## Architecture

### Monorepo Structure

The repository is organized into packages, each with a `BUILD.mk` file:

**Core packages:**
- `libc/`: Core C library functionality
  - `libc/calls/`: System call wrappers
  - `libc/fmt/`: Formatting (printf, etc.)
  - `libc/intrin/`: Intrinsics and optimizations
  - `libc/mem/`: Memory operations (memcpy, etc.)
  - `libc/nexgen32e/`: x86-64 assembly optimizations
  - `libc/nt/`: Windows NT system call wrappers
  - `libc/runtime/`: Runtime initialization
  - `libc/stdio/`: Standard I/O
  - `libc/str/`: String operations
  - `libc/sysv/`: Unix system call wrappers
  - `libc/thread/`: Threading primitives
  - `libc/tinymath/`: Math functions
- `ape/`: Actually Portable Executable loader
- `ctl/`: Cosmopolitan Template Library (C++ STL-like)
- `dsp/`: Digital signal processing
- `net/`: Networking (HTTP, HTTPS, etc.)
- `tool/`: Build tools and utilities
- `test/`: Unit tests mirroring source structure
- `third_party/`: External dependencies
- `examples/`: Example programs

### BUILD.mk Package Files

Each package has a `BUILD.mk` file that defines:
- `PKGS += PACKAGE_NAME`: Register the package
- `PACKAGE_SRCS`: Source files (.c, .cc, .S)
- `PACKAGE_HDRS`: Public headers
- `PACKAGE_OBJS`: Object files (derived from SRCS)
- `PACKAGE_DEPS`: Dependencies on other packages
- `PACKAGE_DIRECTDEPS`: Direct dependencies
- Build rules for binaries and libraries

Dependencies are specified as package names and automatically resolved through the build system.

### Key Build Concepts

**Actually Portable Executables (APE):**
- Binary format that works across operating systems
- Self-extracting polyglot that detects OS at runtime
- Uses MZ (DOS) header with embedded ELF/Mach-O/PE formats

**Build Modes Impact:**
- Binaries include heavy debugging features by default
- `SUPPORT_VECTOR` controls OS support (bitmask)
- `-DNDEBUG` removes assertions
- `-DTINY` removes checks for minimal size
- `-DFTRACE` enables function tracing hooks

**Hermetic Build:**
- Makefile downloads and uses its own toolchain
- Uses `.cosmocc/` directory for compiler
- Sandboxed builds with Landlock Make (Linux)
- Prefer invoking `python3` (not `python`) when running Python scripts or one-liners.

### Debugging

**IMPORTANT: addr2line does NOT work reliably with Cosmopolitan binaries.**

Cosmopolitan APE binaries contain code for multiple platforms (Linux, Windows, macOS, etc.) interleaved together. This confuses addr2line, which may return completely wrong symbols (e.g., Windows NT functions when running on Linux). Do not rely on addr2line for Cosmopolitan debugging.

**Use GDB instead - it works correctly:**
```bash
make -j1 MODE=dbg o//examples/hello
gdb o/dbg/examples/hello.dbg
# Or load symbols separately:
gdb o//examples/hello -ex 'add-symbol-file o//examples/hello.dbg 0x401000'

# Get backtrace at crash:
gdb -batch -ex 'run' -ex 'bt 30' --args ./program args...
```

**Cosmopolitan's built-in debugging facilities:**

| Facility | Header | Description |
|----------|--------|-------------|
| `--strace` | (runtime flag) | Log system calls to stderr |
| `--ftrace` | (runtime flag) | Log function calls to stderr |
| `ShowBacktrace(fd, bp)` | `libc/log/backtrace.internal.h` | Print symbolic backtrace |
| `__die()` | `libc/log/log.h` | Print backtrace and abort |
| `GetSymbolByAddr(addr)` | `libc/log/log.h` | Get symbol name for address |
| `DIEF(fmt, ...)` | `libc/log/log.h` | Fatal error with backtrace |
| `ERRORF/WARNF/INFOF` | `libc/log/log.h` | Logging macros |

**Using ShowBacktrace in code:**
```c
#include "libc/log/backtrace.internal.h"
#include "libc/nexgen32e/stackframe.h"

// Print backtrace to stderr (fd 2)
ShowBacktrace(2, __builtin_frame_address(0));
```

**Note:** ShowBacktrace uses Cosmopolitan's internal symbol table (from the .dbg file), not addr2line, so it works correctly.

**Logging output to file:**
```bash
export KPRINTF_LOG=log
./program --strace
cat log  # View system call log
```

**Manual symbol lookup with nm (when addr2line fails):**
```bash
# Get sorted symbols, then find which function contains an address
nm -n o/dbg/binary.dbg | grep " [Tt] " | less
# Search for addresses just before your target address
```

## Important Patterns

### Cross-Platform Code

- Use `libc/calls/` wrappers instead of raw syscalls
- Check `IsLinux()`, `IsWindows()`, `IsMetal()`, etc. for OS detection
- Windows code uses `libc/nt/` NT API wrappers
- Unix code uses `libc/sysv/` system call wrappers

### Platform Support Vector

The `SUPPORT_VECTOR` macro controls which OSes are supported:
- Bit 0: Linux
- Bit 1: Metal (bare metal/BIOS)
- Bit 3: Windows
- Bit 4: macOS/XNU
- Bit 5: FreeBSD
- Bit 6: OpenBSD
- Bit 7: NetBSD

Example: `SUPPORT_VECTOR=1` means Linux-only.

### Header Structure

- Headers in `libc/isystem/` are the public API (e.g., `stdio.h`, `unistd.h`)
- Internal headers use `libc/integral/` for low-level types
- All source files depend on `libc/integral/normalize.inc`

### Assembly and Intrinsics

- x86-64 assembly goes in `.S` files (preprocessed)
- x86-64 optimizations use `libc/nexgen32e/`
- ARM64 optimizations use `third_party/aarch64/`
- On ARM64, `.S` files compile to empty objects (placeholder system)

## Special Considerations

### APE Loader Installation

On Linux, for optimal performance, install the APE loader:
```bash
sudo ape/apeinstall.sh
```

This registers APE format with binfmt_misc and improves launch time by ~400µs.

### WSL2 Compatibility

If running under WSL2, disable Windows binary interop:
```bash
sudo sh -c 'echo -1 > /proc/sys/fs/binfmt_misc/WSLInterop'
```

### Ruby Development

**Available Ruby ports:**

In the documentation below, `x.y.z` refers to the Ruby version being worked on.

**Directory structure:**

- `third_party/ruby-wip-x.y.z/` → actual Ruby source being ported to Cosmopolitan
- `third_party/ruby-x.y.z/` → original extracted Ruby tarball (pristine reference)

**Important notes:**

- Files created in `ruby-x.y.z` by running (for instance) `./configure …` like `rbconfig.rb` in `ruby-x.y.z/lib/` must be replicated in  `ruby-wip-x.y.z/lib/` by the CosmoRuby build system
- See `RUBY_PORT_PROGRESS.md` for complete Ruby porting documentation

**Build requirements:**
- **Native Ruby x.y.z** required for building CosmoRuby (developers only)
- Install with rbenv: `rbenv install x.y.z`
- The `.ruby-version` file ensures rbenv uses x.y.z
- End users receive packaged `ruby.com` binaries - no Ruby installation needed
- Build system enforces exact version match to avoid rbconfig.rb conflicts
- System Ruby always runs with `--disable-gems` to prevent gem conflicts

**Build targets overview:**

CosmoRuby produces three types of binaries for three different Ruby interpreters:

| Interpreter | Purpose | When to Use |
|-------------|---------|-------------|
| `ruby` | Full interpreter | Main development/distribution target |
| `irb` | Interactive shell | REPL for development |
| `miniruby` | Bootstrap | Build-time code generation only |

For each interpreter, the build produces several artifacts:

| File | Size | Stdlib | Purpose |
|------|------|--------|---------|
| `ruby` | ~6MB | ❌ Needs RUBYLIB | Development testing |
| `ruby.com` | ~15MB | ✅ Embedded | **Distribution** (give to users) |
| `ruby.dbg` | ~35MB | ❌ Needs RUBYLIB | Debugging with gdb |
| `ruby.zipless` | ~6MB | ❌ Needs RUBYLIB | Pre-packaging testing |

**Build commands:**
```bash
# Build base executables (need RUBYLIB environment variable)
make -j1 o//third_party/ruby/ruby
make -j1 o//third_party/ruby/irb
make -j1 o//third_party/ruby/miniruby

# Build debug versions (for use with gdb)
make -j1 MODE=dbg o//third_party/ruby/ruby
```

**See `third_party/ruby/BUILD_TARGETS.md` for complete details on all build artifacts.**

**Running Ruby:**
```bash
# Set RUBYLIB to find standard library
RUBYLIB=$PWD/third_party/ruby-wip-x.y.z/lib o//third_party/ruby/ruby script.rb

# Run IRB (Interactive Ruby)
RUBYLIB=$PWD/third_party/ruby-wip-x.y.z/lib o//third_party/ruby/ruby -e "require 'irb'; IRB.start"

# Or use the packaged ruby.com (with embedded stdlib, no RUBYLIB needed)
ruby.com script.rb
```

**Ruby one-liner best practices:**

**IMPORTANT: Always use single quotes for Ruby `-e` expressions:**
```bash
# ✅ CORRECT - Single quotes prevent shell interpolation
ruby.com -e 'puts "Hello #{RUBY_VERSION}"'
ruby.com -e 'require "json"; puts JSON.generate({a: 1})'

# ❌ WRONG - Double quotes cause shell to eat #{...}
ruby.com -e "puts \"Hello #{RUBY_VERSION}\""  # Prints literal "Hello #{RUBY_VERSION}"
```

**Why:** Ruby string interpolation uses `#{}`, which bash interprets as command substitution with double quotes.

**Inspecting the embedded /zip filesystem:**

Use Ruby itself to inspect embedded stdlib, don't use external tools:
```bash
# ✅ Use Ruby to explore /zip
ruby.com --disable-gems -e 'puts Dir["/zip/**/*"].first(20)'
ruby.com --disable-gems -e 'puts File.exist?("/zip/lib/ruby/x.y.0/rubygems.rb")'
ruby.com --disable-gems -e 'puts File.readlines("/zip/lib/ruby/x.y.0/rubygems.rb").first(10)'

# ❌ Avoid external tools (slower, requires unzip installed)
unzip -l ruby.com | grep rubygems
unzip -p ruby.com zip/lib/ruby/x.y.0/rubygems.rb
```

**Why:** Ruby can directly access its embedded ZIP filesystem - cleaner and more reliable.

**Packaging Ruby for distribution:**

The `third_party/ruby/package_ruby.sh` script creates self-contained Ruby binaries with the standard library embedded as a ZIP filesystem:

```bash
# Build Ruby first
make -j1 o//third_party/ruby/ruby
make -j1 o//third_party/ruby/irb
make -j1 o//third_party/ruby/miniruby

# Package with embedded stdlib
cd third_party/ruby
bash package_ruby.sh
```

**What the packaging script does:**
1. Creates directory structure: `o/cosmo-ruby/lib/ruby/x.y.0/`
2. Copies Ruby stdlib from `third_party/ruby/lib/*`
3. Copies terminfo database for terminal support
4. Extracts any existing ZIP filesystem content from `/zip/`
5. Creates `o/ruby-stdlib.zip` containing all the above
6. Uses `zipcopy` to embed the ZIP into `o/third_party/ruby/ruby.com` and `irb.com`

**Result:** `ruby.com` and `irb.com` are single-file executables with the entire Ruby standard library embedded. They can be distributed and run anywhere without requiring `RUBYLIB` to be set.

**Installation setup:**
```bash
# Symlink packaged Ruby to ~/bin for convenient access
ln -sf $PWD/o/third_party/ruby/ruby.com ~/bin/ruby.com
ln -sf $PWD/o/third_party/ruby/irb.com ~/bin/irb.com

# Copy gem script and symlink it (uses .com extension to avoid conflicts with rbenv/system Ruby)
cp third_party/ruby/bin/gem third_party/ruby/bin/gem.com
chmod +x third_party/ruby/bin/gem.com
ln -sf $PWD/third_party/ruby/bin/gem.com ~/bin/gem.com

# Now ruby.com, irb.com, and gem.com are available on PATH
ruby.com --version
gem.com --version
```

The symlinks automatically pick up new versions when you rebuild and repackage. Using the `.com` extension prevents conflicts with system Ruby or rbenv installations.

### Redbean Development

**Binary locations and naming:**
- Build produces: `o/tool/net/redbean` (no extension)
- Distributed/packaged as: `redbean.com` (with .com extension)
- The `.com` extension is a convention for distribution, not part of the build output

**Creating test binaries with embedded content:**
```bash
# Build redbean
make -j1 o//tool/net/redbean

# Copy and add .com extension for distribution
cp o/tool/net/redbean /tmp/test-redbean.com

# Embed Ruby Rack app (or other content) into the ZIP filesystem
cd /tmp/my-app && zip -r ../app.zip . && cd /tmp && cat app.zip >> test-redbean.com

# IMPORTANT: Use zip -A to fix offsets after appending
zip -A /tmp/test-redbean.com

# Now test-redbean.com contains the embedded app
/tmp/test-redbean.com -p 8080
```

**Why `zip -A` is required:** When you append a ZIP to an existing binary with `cat`, the ZIP central directory offsets are incorrect. The `zip -A` (adjust self-extracting) command recalculates these offsets so the APE can correctly read the embedded ZIP filesystem.

**Redbean Ruby/Rack integration:**
- Ruby scripts with `.rb` extension are executed via `ServeRuby()` function
- Rack interface: Ruby file should return a lambda that responds to `call(env)`
- Returns: `[status, headers_hash, body_array]` per Rack spec
- See `tool/net/redbean.c` lines 3341-3489 for implementation

**Testing Ruby apps in Redbean - Standard workflow:**
```bash
# 1. Create test structure
mkdir -p /tmp/my-test-app
cat > /tmp/my-test-app/hello.rb <<'EOF'
lambda do |env|
  [200, {"Content-Type" => "text/plain"}, ["Hello from Ruby!"]]
end
EOF

# 2. Build and package
make -j1 o//tool/net/redbean
cp o/tool/net/redbean /tmp/my-test.com
cd /tmp/my-test-app && zip -r ../app.zip .
cd /tmp && cat app.zip >> my-test.com
zip -A /tmp/my-test.com  # CRITICAL: Fix ZIP offsets

# 3. Test
/tmp/my-test.com -p 8080 &
REDBEAN_PID=$!
sleep 2
curl http://localhost:8080/hello.rb
kill $REDBEAN_PID
```

**Important routing notes:**
- Files accessed by exact path: `/hello.rb` serves `hello.rb`
- Root `/` shows directory listing, NOT `index.rb` automatically
- Must access Ruby files explicitly: `http://localhost:8080/index.rb`
- Use `-v` flag for verbose request logging

## Releases and Versioning

CosmoRuby uses semantic versioning (vMAJOR.MINOR.PATCH) and GitHub releases.

### Creating a Release

**Before starting:** Check GitHub CLI authentication is valid:
```bash
gh auth status
```
If the token is invalid, re-authenticate with `gh auth login -h github.com`.

**1. Create an annotated tag:**
```bash
git tag -a v1.2.0 -m "$(cat <<'EOF'
CosmoRuby v1.2.0 - Short Description

## New Features
- Feature 1
- Feature 2

## Bug Fixes
- Fix 1

## Performance
| Metric | Before | After |
|--------|--------|-------|
| Speed  | 10s    | 5s    |
EOF
)"
```

**2. Push the tag:**
```bash
git push <remote> v1.2.0
```

**Note:** If you get network errors ("No route to host"), retry after a brief pause:
```bash
sleep 3 && git push <remote> v1.2.0
```

**3. Create GitHub release with binaries using gh CLI:**
```bash
gh release create v1.2.0 \
  --repo <owner>/<repo> \
  --title "CosmoRuby v1.2.0 - Short Description" \
  --notes "$(cat <<'EOF'
## New Features
- Feature 1
- Feature 2

## Usage
\`\`\`bash
ruby.com --version
\`\`\`
EOF
)" \
  o//third_party/ruby/ruby.com \
  o//third_party/ruby/irb.com
```

**Note:** Same network retry advice applies - prefix with `sleep 3 &&` if needed.

**Important:** Always include `ruby.com` and `irb.com` binaries in releases so users can download them directly.

### Version Number Guidelines

- **MAJOR** (v2.0.0): Breaking changes, major Ruby version bumps
- **MINOR** (v1.2.0): New features, non-breaking improvements
- **PATCH** (v1.2.1): Bug fixes, documentation updates

## CRITICAL RULE: DO NOT MODIFY COSMOPOLITAN CORE FILES

**NEVER modify core Cosmopolitan files without explicit approval:**
- `Makefile` - Only add `include` statements for third_party packages
- `build/*.mk` - Core build system files
- `tool/build/*` - Build tools (mkdeps, compile, etc.)
- `libc/*` - Core library code
- Any file outside `third_party/` or `examples/`

**If modifications are needed:**
1. Create a new tool/file in `third_party/` (e.g., `mtsh` instead of modifying `cocmd`, `mtdeps` instead of modifying `mkdeps`)
2. Document why the separate tool is needed
3. Use Make variable overrides or environment variables to opt-in to the new behavior
4. Never change default Cosmopolitan behavior

**Why this matters:**
- Cosmopolitan is a well-tested, stable codebase used by many projects
- Modifications to core files make it impossible to merge upstream changes
- Bugs in core modifications affect the entire build system
- Third-party code should be isolated and self-contained

## Shell Script Patterns

### Finding the repo root

**NEVER** use relative `../..` chains from `SCRIPT_DIR` to derive `REPO_ROOT`. These break when a script is moved, symlinked, or invoked from an unexpected location.

```bash
# ❌ WRONG - fragile, assumes script lives at a fixed depth
SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
REPO_ROOT="$SCRIPT_DIR/../.."

# ✅ CORRECT - works from any directory inside the repo
REPO_ROOT="$(git rev-parse --show-toplevel)" || { echo "Error: not inside a git repo"; exit 1; }
```

Keep `SCRIPT_DIR` only if the script needs it for other purposes (e.g., calling sibling scripts). Otherwise drop it entirely.
